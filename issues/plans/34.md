# Issue #34: Github development deploy actions are trigged off bot authored branch pushes.

**Verdict:** bug
**Status:** in-review
**Branch:** `issue-34`

## Summary

`deploy-site.yml` triggers on every push to every branch (except `dependabot/**`),
which means the commits the `issue-triage`/`issue-work` automation pushes to
`issue-{n}` branches (authored as `claude[bot]`, per `.github/workflows/issue-triage.yml`)
also trigger a full test/scaffold/local-smoke run and a real `development` deploy
via `qpq go:docker`, even though those pushes are just plan-file edits or WIP
commits with no reason to be deployed.

## Affected packages

- `.github/workflows/deploy-site.yml`: the push trigger and the `deploy` job's
  gate need to exclude bot-authored pushes.

## Approach

1. In `.github/workflows/deploy-site.yml`, extend the `deploy` job's existing
   `if` (currently `github.event_name == 'workflow_dispatch' || github.ref_name
   != 'main'`) with an additional `&& !endsWith(github.actor, '[bot]')` clause,
   so a bot-authored push (`claude[bot]`, `github-actions[bot]`, etc.) still
   runs the test/scaffold/local-smoke gates but never reaches the AWS deploy
   step. This mirrors the existing `!dependabot/**` branch exclusion already
   on the `push:` trigger, using the same "skip bots" intent.
2. Update the comment block at the top of the file (lines 3-8) to note that
   bot-authored pushes are gated out of the deploy step, so the branch mapping
   description stays accurate.
3. Leave `test`, `scaffold`, and `local-smoke` running for bot pushes for now:
   the issue is specifically about deploys, and those jobs are cheap CI
   validation rather than a real deploy. This can be revisited later if bot
   pushes turn out to be frequent enough for that CI cost to matter too.

This is a stopgap per the issue: the reporter notes a deploy label or approved
PRs will later be used to let bot-authored work be deployed deliberately. That
is out of scope for this plan.

## Open questions

- [ ] Is `claude[bot]` (via the GitHub App backing `CLAUDE_CODE_OAUTH_TOKEN`)
  actually the `github.actor`/pusher recorded on these pushes, or does the
  push show up under a different identity (e.g. `github-actions[bot]`) in
  practice? The `endsWith(github.actor, '[bot]')` check should cover either
  case, but confirming against an actual `issue-{n}` push run would be good
  before merging.
