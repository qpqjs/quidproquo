# Issue #49: EventDoc summary and snapshots can be projected mid-burst, leaving derived views permanently behind the log

**Verdict:** bug
**Status:** ready
**Branch:** `issue-49`

## Summary

The events-store stream projector projects a document at the sort key of whichever record survived coalescing, and that record is not always the burst's newest event. When it is not, the summary row and snapshot set land mid-burst and nothing ever moves them to the log head. The fix is to project at the log's current head instead of at the delivered record's sort key.

## Affected packages

- `quidproquo-features`: `eventDoc/entry/kvsStream/eventDocSummaryProjector.ts` picks the projection target from the record's sort key; `eventDoc/logic/askEventDocProjectAtEvent.ts` and `askEventDocSummaryRederive.ts` do the fold and write. The fix and its tests live here.
- `quidproquo-actionprocessor-awslambda`: `getActionProcessor/core/event/dynamo/streamEvent/getEventGetRecordsActionProcessor.ts` is where `coalesceByPartitionKey` keeps the batch's last record per partition key. Its comment claims the stream orders records within a partition key, which is the assumption the projector relied on. Comment and docs fix only; no behaviour change.
- `quidproquojs.com` (docs): `docs/config/core/key-value-store.md` and `docs/config/features/event-doc-summary.md` describe coalescing as "the latest" record and the snapshot as "the batch's newest event". Both need the wording corrected.

## Approach

Root cause first. DynamoDB Streams only order records for the same item (same pk and sk). Events in one document share a pk but each has its own sk, so they are different items and the stream may deliver them in any order within a batch. A burst appended by `askEventDocEventWriteMany` goes through `TransactWriteItems` in one call, which makes interleaving likely for larger bursts, matching the report that 4-event bursts projected cleanly and a 27-event burst did not.

`coalesceByPartitionKey` in the AWS Lambda processor keeps the last record per (scope, pk) in batch order. With interleaved delivery that is an arbitrary event from the burst (sk 17 in the report), not the max sk. `askEventDocProjectStreamRecord` then calls `askEventDocProjectAtEvent(modelId, Number(record.keys.sk), ...)`, which folds `upToEventId: 17` and writes the snapshot set at 17 and the summary row from it. Events 18 to 26 are in the store but no later stream record exists for that document, so nothing re-triggers.

The processor cannot fix this itself: it is generic and does not know that `sk` is a log position, and a projector that "re-derives from source" should not depend on which record survives anyway.

Steps:

1. `quidproquo-features/src/eventDoc/entry/kvsStream/eventDocSummaryProjector.ts`: in `askEventDocProjectStreamRecord`, stop reading the event id off `record.keys.sk`. For the non-Remove path with a functions name, read the head with `askEventDocEventLast(modelId, { consistentRead: true })` (already exists in `eventDoc/data/`, used by `askEventDocDocumentStateLatest`). If the head is null, fall through to `askEventDocSummaryRederive(modelId)` (an empty log deletes the summary row, which is the right outcome). Otherwise call `askEventDocProjectAtEvent(modelId, head.payload.metadata.eventId, functionsName)`. The Remove branch and the no-functions branch already rederive from the whole log and are unchanged.

   After the projection returns, log one `askLogCreate(LogLevelEnum.Info, ...)` line carrying `modelId`, the head event id projected to, and the delivered record's `sk`. A stale document can then be checked against the projector's own record of what it did and when, instead of by folding the log by hand. Do not add a post-write "projected id versus head" comparison: the projected id is the consistently read head by construction, so the two can only differ when events landed after the head read, and those carry their own stream records and re-trigger the projector. A check there would only ever report that race, never a real gap.

2. Same file: rewrite the two comments. The JSDoc on `projectEventDocSummary` must say the record only signals that the document changed and the projection always targets the current log head, so it does not matter which record of a burst survives coalescing or how the stream ordered them. The inline comment above `askEventDocProjectStreamRecord` keeps its Remove explanation.

3. `quidproquo-features/src/eventDoc/logic/askEventDocProjectAtEvent.ts`: no logic change. The seed short-circuit (`seed?.eventId === eventId`) already makes a second delivery for the same head a cheap summary rewrite, and the consistent event reads already guarantee the fold sees every event up to the head it just read. Update the JSDoc's first line so it reads as "project a document at a given event, normally the head".

4. `quidproquo-features/src/eventDoc/logic/askEventDocSummaryRederive.ts`: pass `consistentRead: true` to `askEventDocEventListAll`. It is the projector's fallback and runs right after the append that triggered the stream, so an eventually consistent read can miss the burst's tail in exactly the same way. Update the JSDoc to state the read is consistent.

5. `quidproquo-features/src/eventDoc/entry/kvsStream/eventDocSummaryProjector.spec.ts`:
   - Replace the test `folds the PREFIX up to the stream record, not the whole log` with its inverse: a record for sk 1 arriving when the log already holds sk 2 must fold `[0, 1, 2]` and write the snapshot set at sk 2. Its comment explained why folding past the record's id would mislabel the snapshot; the new behaviour labels the snapshot at the head it folded to, so that concern no longer applies.
   - Add a regression test for the report: log of many events (say 0 to 26), stream record whose `keys.sk` is a mid-burst event (17). Assert the fold receives every event, the snapshot rows sit at sk 26, and the summary row is written. Assert `foldCalls` has length 1.
   - Add a test that a second delivery for a head that already has a complete snapshot set does not fold again (this is the existing incremental-path short-circuit, now reached via the head read).
   - Add a test that a non-Remove record for a document whose log is empty (consistent head read returns null) deletes the summary row rather than folding.
   - Update the `describe('projectEventDocSummary snapshots')` comment block and the test title `stores one row per view the fold returns, keyed at the batch newest event` to say "keyed at the log head". The mock KVS query in `buildMocks` already honours `sortAscending: false` and `limit: 1`, so `askEventDocEventLast` works against it without changes; check the `consistentRead` option is simply ignored by the mock.

6. `quidproquo-actionprocessor-awslambda/src/getActionProcessor/core/event/dynamo/streamEvent/getEventGetRecordsActionProcessor.ts`: fix the comment above `coalesceByPartitionKey`. The stream orders records per item, not per partition key, so "last in the batch" is the last delivered record for that key, not necessarily the newest write. A coalescing consumer must re-derive from source rather than trust the surviving record's image or sort key. No code change. The existing test `coalesces to the LAST change per document` in `streamEvent.test.ts` still holds (it asserts delivery-order semantics); rename it to say "last delivered" so it does not restate the wrong guarantee.

7. `quidproquo-core/src/types/KvsStreamEvent.ts`: the trailing comment says "Ordering is guaranteed per partition key". Change it to per item (partition key plus sort key), matching DynamoDB's actual guarantee.

8. Docs in `quidproquojs.com/docusaurus/docs/config/core/key-value-store.md`: the `coalesceByPartitionKey` row says "(the latest)" and the paragraph above the table says records for a partition key are always delivered in order. Correct both: ordering is per item, coalescing keeps the last delivered record, and a handler must re-derive from source. `docs/config/features/event-doc-summary.md` item 3 says the projector persists the snapshot "as of the batch's newest event"; change to "at the log head at the time the handler runs".

9. `quidproquo-features/src/eventDoc/config/defineEventDocSummary.ts`: the comment on the events store says "coalescing makes one burst one rebuild". Still true; leave it, or add "at the log head" if it reads better after step 2.

10. Run `npm run test -w quidproquo-features` and `npm run test -w quidproquo-actionprocessor-awslambda`, then `npm run lint`.

Out of scope: a backfill for documents already projected mid-burst. Any new event on such a document now re-projects it to head, and a one-off rederive can be triggered by appending a no-op event or by calling `askEventDocSummaryRederive` from a script. Mention this in the PR description so the reporter knows how to repair the stale documents they found.
