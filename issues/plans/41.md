# Issue #41: deployed-smoke `eventDocConcurrentAppend` found 100 events instead of 101

**Verdict:** bug
**Status:** ready
**Branch:** `issue-41`

## Summary

The `eventDocConcurrentAppend` smoke test fans 100 writers out on a queue, each appending one event to the same fresh document, and expects all 100 to land (101 events with `INIT_STATE`). On the second root of the run linked in the issue, one writer never landed. The reporter wants to know why, and for the test to stop flaking.

Everything below is against PR #40's head (`version-bump`, commit `00bd5b62`). None of the event-doc or smoke code exists on `main` yet, so this branch is planning only; implement on top of `version-bump` (or on `main` once #40 merges).

Diagnosis: the append contract and the queue defaults combine so that a writer which loses the slot race too many times is dropped on the floor, with no second chance inside the test's polling window.

1. `askRunEventDocConcurrentAppendTest` (`quidproquojs.com/apps/qpqjs/services/test/service/src/smoke/tests/eventDoc/askRunEventDocConcurrentAppendTest.ts`) sends `SMOKE_PROBE_DOC_WINDOW` (100) messages to `smokeEventDocAppends` at once. `defineSmoke.ts` declares that queue with no options, so `defineQueue` (`quidproquo-core/src/config/settings/queue.ts`) gives it `maxTries: 1`, `ttRetryInSeconds: 900`, `batchSize: 0`. With `batchSize` 0 the CDK construct (`QpqApiCoreQueueConstruct.ts`) omits the batch size, so Lambda's SQS poller uses its default of up to 10 records per invocation, and `askProcessEvent` (`quidproquo-core/src/stories/askProcessEvent.ts`) runs those records with `askMapParallel`. So the writers race both inside an invocation and across invocations; effective contention on the one partition key is tens of writers at once.

2. Each writer calls `askEventDocAppendServerEvent`, which runs `askEventDocEventAppend` (`quidproquo-features/src/eventDoc/logic/askEventDocEventAppend.ts`). That loop reads the head (consistent), conditionally writes `head + 1`, and on `Conflict` re-laps via `askRetry` at most `EVENT_DOC_APPEND_MAX_RETRIES = 8` times, with `20ms` linear backoff and at most `40ms` jitter (`quidproquo-features/src/eventDoc/constants/eventDocAppendRetry.ts`). Total sleep across all 8 retries is roughly `20 * 36 + 8 * 20 = ~880ms`. Exactly one writer wins each slot, so a burst of tens of simultaneous writers cannot converge inside 9 attempts; whether a given writer loses 9 laps in a row depends on how staggered the Lambda invocations happen to be. The docs (`ask-event-doc-event-append.md`, Notes) say exhausting the retries means "something is hammering it, not ordinary concurrent editing". The test is, by design, hammering it.

3. When the 9th attempt loses, `askEventDocEventAppend` throws `Conflict`, `onSmokeEventDocAppend` propagates it, and `getEventTransformResponseResultActionProcessor` reports the record as a `batchItemFailure`. Because `maxReceiveCount` is 1, SQS moves the message straight to `smokeEventDocAppends-dead`. It is never redelivered. Even with a higher `maxTries`, the visibility timeout is 15 minutes, far outside the 40 second window `askAwaitSmokeEventDocLog` polls for (20 attempts of 2 s).

4. Result: the log holds `INIT_STATE` plus 99 marks, which is the "expected 101, found 100" in the issue. The first root passed because Lambda's poller ramp-up and cold starts spread its writers out enough; the second root got a tighter burst. The `eventDocInterleavedBatchAppend` test has only 10 writers, which is inside the retry budget, so it passes.

A second, independent way to lose exactly one writer exists in the same path and should be closed while we are here: `sendMessages` (`quidproquo-actionprocessor-awslambda/src/logic/sqs/sendMessages.ts`) sends 100 messages as 10 `SendMessageBatch` calls and never looks at the response's `Failed` array. SQS can reject individual entries without the call throwing, so a partially failed batch would silently drop a writer and produce the identical symptom. Nothing in the failing run points at this specifically, but the test cannot tell the two apart today.

## Affected packages

- `quidproquo-features`: `askEventDocEventAppend` / `askEventDocAppendServerEvents` share the retry budget in `constants/eventDocAppendRetry.ts`; it is too small for a burst of tens of writers on one document.
- `quidproquo-actionprocessor-awslambda`: `logic/sqs/sendMessages.ts` ignores partial failures from `SendMessageBatch`.
- `quidproquojs.com` (`apps/qpqjs/services/test/service`): the smoke queue config, the writer handler, and the poll/assert helpers for the event-doc tests.
- `quidproquojs.com/docusaurus`: the append docs describe the retry bound and need to match whatever it becomes.

## Approach

1. Confirm the diagnosis against the failing run before changing anything. In the development account, look at the `smokeEventDocAppends-dead` queue for a message whose payload has `runId` `a9dc38b4-e46d-4462-a339-2df44476c263` and `docId` `f2823236-50a0-46a3-a040-e1814a330707`, and search the queue lambda's CloudWatch logs for `lost the slot race 8 times`. A dead-lettered message with that docId confirms step 3 above. An empty DLQ with no Conflict log line points at the `SendMessageBatch` partial failure instead (step 3 of this list still fixes it).

2. `quidproquo-actionprocessor-awslambda/src/logic/sqs/sendMessages.ts`: after each `SendMessageBatchCommand`, check `response.Failed`. If it is non-empty, throw an error naming the queue and the failed entry ids and messages (`Failed[].Id`, `.Code`, `.Message`), so `askQueueSendMessages` fails loudly instead of quietly dropping entries. Extend `sendMessages.test.ts` with a case where the mocked client returns one `Failed` entry and assert the helper rejects.

3. `quidproquo-features/src/eventDoc/constants/eventDocAppendRetry.ts`: widen the slot-race budget so a burst of tens of writers converges. Proposed: `EVENT_DOC_APPEND_MAX_RETRIES` 8 to 20 and `EVENT_DOC_APPEND_RETRY_MAX_JITTER_MS` 40 to 100, base wait unchanged at 20 ms. Worst case sleep becomes about `20 * 210 + 20 * 100 = 6.2s` plus lap I/O, still well inside a queue lambda or API Gateway timeout, and the larger jitter is what actually de-synchronises a burst so later laps stop colliding. Update the comment on the constants to say what contention level the budget is sized for. Both the single and batch appends read these constants, so nothing else changes.

4. `quidproquo-features/src/eventDoc/logic/askEventDocEventAppend.test.ts` (new): mirror the mock style of `askEventDocAppendServerEvents.test.ts` (`buildMocks` with `heads` and `conflicts`) and cover: (a) a writer that loses `EVENT_DOC_APPEND_MAX_RETRIES` laps and wins the next one lands at the advanced head with one `Conflict` per lost lap and one `askDelay` per lost lap; (b) a writer that loses `EVENT_DOC_APPEND_MAX_RETRIES + 1` laps throws `ErrorTypeEnum.Conflict` with the "lost the slot race" message. Use `runStory` and mock `KeyValueStoreActionType.Upsert` to return the namespaced `Conflict` error `conflicts` times. Assert against the constant, not a literal, so step 3 does not silently break the test.

5. `quidproquojs.com/apps/qpqjs/services/test/service/src/smoke/config/defineSmoke.ts`: give the `smokeEventDocAppends` queue a redelivery path so a writer that still exhausts the in-process budget is retried rather than dead-lettered: `defineQueue(SMOKE_EVENT_DOC_APPEND_QUEUE, {...}, { maxTries: 3, ttRetryInSeconds: 30 })`. `ttRetryInSeconds` is also the queue lambda's timeout, so 30 s is the floor that still comfortably covers one handler run (`askEventDocProvideStore` plus one append, seconds at most). Note in the comment that a redelivered message re-runs the whole append: that is safe because a lost slot race writes nothing, but a handler that times out after its write would land a duplicate mark, and the `===` assert in `askAwaitSmokeEventDocLog` would then fail with "found 102", which is the right outcome.

6. `smoke/tests/eventDoc/askAwaitSmokeEventDocLog.ts`: raise the window to cover one redelivery, e.g. `POLL_ATTEMPTS` 20 to 50 at 2 s (100 s total; passing runs still exit as soon as the count is reached). Improve the assertion message: when the count is short, list the `writerId`s that are missing by comparing the `SMOKE_MARK` events' `writerId` against the expected set, so the next failure says which writer was lost instead of just how many. That needs the expected writer ids passed in (or the expected count plus the mark events), so change the signature to take `expectedWriterIds: number[]` and derive `expectedLength` as `expectedWriterIds.length + 1`. Update both callers (`askRunEventDocConcurrentAppendTest.ts`, `askRunEventDocInterleavedBatchAppendTest.ts`).

7. `smoke/queue/onSmokeEventDocAppend.ts`: fix the comment that says "Every message is its own invocation". With `batchSize` 0 the poller hands up to 10 records to one invocation and `askProcessEvent` runs them in parallel, so the race is both intra- and inter-invocation. Either keep that (it is a harder test) and say so, or set `batchSize: 1` on the queue in step 5 to make the comment true. Recommendation: keep the default and fix the comment; the tighter race is the point of the test.

8. `quidproquojs.com/docusaurus/docs/actions/features/event-doc/ask-event-doc-event-append.md` (Notes) and `ask-event-doc-append-server-event.md` if it repeats the bound: state the new retry count, the backoff shape, and roughly what burst size the budget is meant to absorb, and keep the sentence that exhaustion is a `Conflict` the caller must handle (a queue consumer should let the queue redeliver, which is what step 5 does). Also add a line to `docs/config/core/queue.md` if it does not already spell out that `maxTries` defaults to 1, so a failed message dead-letters on first failure unless the queue opts in to retries.

9. Verify: `npm run test -w quidproquo-features` and `npm run test -w quidproquo-actionprocessor-awslambda` for the unit tests; `npm run lint`. Then deploy development and run `quidproquojs.com/scripts/deployedSmoke.mjs` against both roots several times in a row (the failure is intermittent, one pass proves nothing). Check the `smokeEventDocAppends-dead` queue is empty afterwards.

## Open questions

- [ ] Do we want the framework-side budget increase (step 3), or should the framework keep its small budget and only the smoke queue get redelivery (step 5)? Step 3 changes behaviour for every event-doc writer under contention (a request can now spend up to about 6 s before failing with `Conflict`); step 5 alone fixes the test but leaves `askEventDocEventAppend` unable to absorb a burst of a few dozen writers, which real fan-out consumers will hit too. The plan does both; drop step 3 if that latency ceiling is unwanted.
- [ ] Is anyone able to check the development account's `smokeEventDocAppends-dead` queue for the run in the issue (step 1)? It would settle whether this run was the retry cap or a `SendMessageBatch` partial failure. Not blocking: both are fixed here.
