# Issue #58: go:docker: build once and deploy/publish from the saved build, so a CI deploy can run one runner per service

**Verdict:** enhancement
**Status:** in-progress
**Branch:** `issue-58`

## Summary

Split `qpq go:docker` into two modes that can run on different machines: `--build-only` runs today's Phase 1 (workspace build, synth, api/views/remote bundles, CDK synth) and leaves everything a deploy needs under one directory per service; `--from-build` runs the chosen deploy phase (inf, api, web or views) for a service from that directory without rebuilding, and after an api deploy publishes the service's federated remote. A CI pipeline can then run a build matrix once, then an inf matrix, then api and web matrices, then views, keeping the two cross-service orderings a single `go:docker all all` enforces today. Separately, `GO_DOCKER_BUILD_CONCURRENCY` defaults to the machine's core count instead of 4.

## Affected packages

- `quidproquo-cli`: owns `go:docker` end to end. `src/commands/goDocker.ts` parses the args, `src/platforms/aws/goDocker.ts` is the whole build-then-deploy orchestration, `src/platforms/types.ts` declares the driver surface, `src/cli/commandRegistry.ts` prints the usage, and `src/platforms/docker/index.ts` is the other driver that implements `goDocker`. `README.md` documents the command.
- `docs/quidproquo-cli-design.md` and `CHANGELOG.md` at the repo root: the design note describes the current single-run shape and the concurrency default; the changelog needs a line.

Nothing changes in `quidproquo-deploy-awscdk` or `quidproquo-deploy-rspack`. The CDK assembly that `cdk synth --output` writes already stages the lambda bundles as assets (`Function.ts` uses `Code.fromAsset` on the api build path), so after synth the deploy needs the assembly only, not the api bundle. The views bundle and the federated remote are plain directories that the existing docker waves already sync from disk.

## Approach

The deploy phases in `awsGoDocker` today take three things from the live workspace that a cold runner will not have: the per-service CDK assembly under `dist/qpq/cdk-docker/<app>/<service>`, the views dist and remote publish dir under `dist/apps/<app>/services/<service>/`, and a handful of values resolved by loading `infrastructure.ts` through `loadServiceQpqConfig` (stack names, views S3 destinations including the shell's views bucket, the federated store bucket and prefix, which services have views or federation). Loading `infrastructure.ts` needs the workspace packages built, which is the expensive step the issue wants to run once. So the build mode resolves those values while it still has the live config and writes them to a small manifest next to the outputs, and the deploy mode reads only the manifest and the directories.

1. **Define the saved build layout and its manifest** in a new `quidproquo-cli/src/platforms/aws/goDockerBuildOutput.ts`:

   - `getGoDockerBuildDir(appName, serviceName)` returns `dist/qpq/go-docker/<app>/<service>`. Replace the private `assemblyDir` in `goDocker.ts` with `<buildDir>/assembly`. The views copy goes to `<buildDir>/views`, the remote publish dir to `<buildDir>/remote`, the manifest to `<buildDir>/deploy.json`. One directory per service, so a CI job uploads `dist/qpq/go-docker/<app>/<service>` as its artifact.
   - `GoDockerBuildManifest` type: `{ cdkVersion: string; stacks: { inf: string; api: string; web: string } | null; views: { destinations: string[] } | null; remote: { manifestHash: string; bucketName: string; servicePrefix: string } | null }`. `stacks` is null when the build ran with `views` only (no synth happened), `views` is null when the service has no `views/` dir or views were not requested, `remote` is null when the service has no `defineFederatedModuleStore` or api was not requested. `cdkVersion` is the `aws-cdk` version `buildDeployerImage` already reads, so the deploy side can refuse an assembly synthesized by a different CLI version.
   - `writeGoDockerBuildManifest(appName, serviceName, manifest)` and `readGoDockerBuildManifest(appName, serviceName)`. The reader throws with the directory in the message and the fix (`run qpq go:docker <service> --build-only first`) when `deploy.json` is missing, following the message shape of `resolvePublishTarget` in `remote.ts`.
   - A unit test `goDockerBuildOutput.test.ts` (vitest is already configured for the package) that round-trips a manifest through a temp dir and checks the missing-manifest error names the directory.

2. **Add the mode to the driver surface.** In `src/platforms/types.ts` add `export type GoDockerMode = 'full' | 'build-only' | 'from-build'` and change `goDocker?` to `(appName: string, plan: DeployPlan, mode: GoDockerMode) => Promise<void>`. In `src/platforms/docker/index.ts` wrap `dockerGo` so a mode other than `full` prints that the docker platform builds and deploys in one step (the same shape as the existing `publishNotSupported`) and exits 1, instead of silently running the full build.

3. **Parse the flags** in `src/commands/goDocker.ts` with `hasArgFlag` from `lib/args.ts` (`getPositionalArgs` already skips `--` tokens, so `qpq go:docker all all --build-only` still yields the positional plan). Both flags together is an error. Either flag with an `account`, `domain` or `bootstrap` plan is an error: those stacks deploy host-side through the workspace CDK app and have no saved form. Pass the mode as the third argument to `driver.goDocker`. Pull the flag-to-mode logic into a small exported `resolveGoDockerMode(argv): GoDockerMode` in `src/lib/goDockerMode.ts` with a test alongside (`args.test.ts` shows the style), since it is the one piece of the command that is pure.

4. **Split `awsGoDocker` in `src/platforms/aws/goDocker.ts` into a build half and a deploy half**, with the existing function becoming the `full` mode that calls both in sequence.

   `buildGoDockerOutput(appName, plan)` is today's Phase 1 with these changes:
   - It still runs `runAppHook(appName, 'predeploy')`, the workspace build, the in-process synths, the api bundles, the views bundles, the remote bundles and the CDK synths, with the same `stacks` gating as now. The synth output dir becomes `<buildDir>/assembly`; the `fs.rmSync` before it clears the whole `<buildDir>` so a stale `views/` or `remote/` from a previous build cannot survive a stack-type change.
   - After the views and remote bundles, copy `getViewsDistDir(appName, service)` to `<buildDir>/views` and the `service-remote-published` dir to `<buildDir>/remote` with `fs.cpSync(..., { recursive: true })`. The bundlers keep writing to their current paths (`getViewsRspackConfig` and `publishFederatedRemote` decide those), so nothing in `quidproquo-deploy-rspack` moves. Export `getPublishPath` from `remote.ts` (it is private today) so the copy can find the remote dir.
   - Resolve the manifest values while the live config is loaded: stack names via `qpqDeployAwsCdkUtils.get{Inf,Api,Web}StackName` (the existing `stackNames` map), views destinations via `getViewsS3Destinations` from `viewsSync.ts` (this loads the shell config, which is why the current code synths `shell` whenever views are needed; keep that), the remote target via `resolvePublishTarget` from `remote.ts`. Write `deploy.json` last, after every copy, so a manifest only ever exists next to a complete build.
   - `cdk synth` still performs `fromLookup` context lookups (hosted zones, and the VPC for a graph database or VPC-attached api), so the build mode keeps the `isAwsCredentialsValid` check and needs AWS credentials in the build job. Say so in the README.
   - The docker preflight (`assertDockerRunning`, `buildDeployerImage`, `docker pull` of the aws-cli image) moves out of the build half: a build runner needs no docker daemon.

   `deployGoDockerOutput(appName, plan)` is today's Phases 2 to 5 reading only manifests:
   - Read every selected service's manifest up front, so one missing build fails the job before any container starts (same reason `awsPublishUpload` resolves all targets first). Refuse a manifest whose `cdkVersion` differs from the CLI's own `aws-cdk` version with a message naming both versions. When the plan asks for `inf`, `api` or `web` and the manifest's `stacks` is null, or asks for `views` and `views` is null, fail with the stack type the build was made for.
   - `viewServices` becomes the selected services whose manifest has `views`; `federatedServices` becomes those whose manifest has `remote` (only when `needApi`, as now).
   - `dockerDeployStack` takes the assembly dir as a parameter instead of calling `assemblyDir`. `dockerSyncViews` takes the views dir and the destination list instead of calling `getViewsDistDir` and `getViewsS3Destinations`. `dockerPublishRemote` takes the remote dir and the `{ manifestHash, bucketName, servicePrefix }` from the manifest instead of calling `resolvePublishTarget`. The container commands themselves do not change.
   - Phase order stays inf, then api and web, then views, then publish. With `--from-build api` on one service that is: deploy the api stack, then publish its remote, which is the pairing the issue needs per job. With `--from-build all` on one service all four phases run from the saved output.
   - The docker preflight runs here with its current conditions.

   `awsGoDocker(appName, plan, mode)` keeps the `cancelled`, `account` and `bootstrap` branches as they are (the command already rejects those with a non-full mode), then runs the build half, the deploy half, or both. Keep the `isAwsCredentialsValid` check in all three modes. Rewrite the header comment of the file to describe the three modes and the saved layout; drop the sentence about where the assembly used to live.

5. **Default the build concurrency to the core count.** In `goDocker.ts` replace `|| 4` with `|| os.availableParallelism()` (Node 18.14+, and the repo's `.nvmrc` is 24). Keep the env var as the override. Update the knob comment at the top of the file and the sentence in `docs/quidproquo-cli-design.md` that says "default 4".

6. **Usage and docs.**
   - `src/cli/commandRegistry.ts`: give `go:docker` a `usageArgs` of `[svc] [stack]` and `usageExtra` lines for `--build-only` (build and save to `dist/qpq/go-docker/<app>/<svc>`, no docker needed) and `--from-build` (deploy the chosen stack from that directory, no rebuild; an api deploy also publishes the federated remote).
   - `quidproquo-cli/README.md`: extend the `qpq go:docker` row, and add a short paragraph under the deploy section describing the CI shape: a build matrix with `--build-only` uploading each service's directory as an artifact, then `--from-build inf` for every service, then `--from-build api` and `--from-build web`, then `--from-build views`, each job downloading its artifact first. Mention that the build job needs AWS credentials for the synth lookups, that the deploy jobs need docker, and that `GO_DOCKER_BUILD_CONCURRENCY` now follows the core count.
   - `docs/quidproquo-cli-design.md`: update the `qpq go:docker` bullet to mention the two modes.

7. **Changelog.** Under the next version in `CHANGELOG.md`: `cli: \`qpq go:docker\` gains \`--build-only\`, which builds and saves everything a deploy needs under \`dist/qpq/go-docker/<app>/<service>\`, and \`--from-build\`, which deploys one stack (and after api, publishes the federated remote) from that directory without rebuilding, so a CI deploy can run one job per service and phase. \`GO_DOCKER_BUILD_CONCURRENCY\` defaults to the machine's core count`. Add to the breaking changes section: the assembly moves from `dist/qpq/cdk-docker/<app>/<service>` to `dist/qpq/go-docker/<app>/<service>/assembly`, and `QpqPlatformDriver.goDocker` takes a third `mode` argument. Both only affect anything that reads those paths or implements a driver outside this repo.

8. **Verify.** `npm run test -w quidproquo-cli` for the two new test files, `npm run lint -w quidproquo-cli`, `npm run build -w quidproquo-cli`. Then, against a real deployment, `qpq go:docker all all --build-only`, delete `node_modules` of the workspace packages' `lib/` (or run from a fresh checkout with only `npm ci`), and run `qpq go:docker <svc> inf --from-build`, `<svc> api --from-build`, `<svc> views --from-build` for a service that has views and federation, checking the publish lands after the api stack. Finally one plain `qpq go:docker all all` to confirm the full mode is unchanged.

Out of scope here but worth a follow-up: switching `.github/workflows/deploy-site.yml` to the matrix shape, which would be the first real use of the two modes.

## Open questions

- [x] Is one directory per service worth the copy? No: the manifest points at the dirs the bundlers already write. The plan copies the views and remote dirs into `dist/qpq/go-docker/<app>/<service>` so a CI job uploads a single path. The alternative, leaving them in `dist/apps/<app>/services/<service>` and recording the paths in the manifest, avoids the copy but makes the artifact three paths. Not blocking: with no answer, implement the copy.
