# Issue #53: Dashboard anomaly detectors are keyed by list index, so adding a lambda fails the stack with AlreadyExists

**Verdict:** bug
**Status:** ready
**Branch:** `issue-53`

## Summary

`QpqConfigAwsDashboardConstruct` gives each lambda duration `CfnAnomalyDetector` a construct id of `duration-anomaly-detector-${index}`, so adding a lambda shifts every later detector onto a different function's metric and the next deploy fails with `AlreadyExists` when CloudFormation creates the moved detector before deleting the one already on that metric. The detector id should be derived from the lambda it watches, so an added lambda adds one detector and moves none.

## Affected packages

- `quidproquo-deploy-awscdk`: owns `QpqConfigAwsDashboardConstruct`, where the index-keyed ids are built.

## Approach

The whole fix lives in `quidproquo-deploy-awscdk/src/constructs/feature/config/dashboard/QpqConfigAwsDashboardConstruct.ts`.

1. **Carry the undecorated lambda key alongside its function name.** `getServiceLambdaFunctionNames` (line 25) builds a list of base names such as `orders-route`, `sendEmail-sfunc`, `jobs-queue`, `nightly-SE`, `chat-ws`, then maps each through `awsNamingUtils.getConfigRuntimeResourceNameFromConfig` and throws the base name away. Change it to return `{ key, functionName }[]` where `key` is that base name and `functionName` is the decorated name used today. Declare the pair type in the same file, not exported (`type ServiceLambda = { key: string; functionName: string }`), and rename the helper to `getServiceLambdas`. The base names are unique within a service because every category carries its own suffix, so `key` is safe to use as a construct id.

2. **Key the detector by the lambda, not the index.** At line 182, replace `functionNames.forEach((functionName, index) => ...)` with a loop over the pairs and use `duration-anomaly-detector-${key}` as the construct id. This mirrors the api latency detector at line 106, which already uses `latency-anomaly-detector-${apiConfig.apiName}`. No manual hashing is needed: CDK builds the logical id from the construct path plus an 8 character hash, strips non-alphanumerics and bounds the length itself.

3. **Update the four lambda widgets** (lines 161 to 176) to map over `serviceLambdas.map(({ functionName }) => ...)`. Widget output is unchanged.

4. **Add `QpqConfigAwsDashboardConstruct.test.ts`** next to the construct, following the synth pattern in `quidproquo-deploy-awscdk/src/constructs/feature/core/storageDrive/QpqCoreStorageDriveConstruct.test.ts`. Build the config with `buildTestQpqConfig([defineAwsServiceAccountInfo('123456789012', 'ap-southeast-2'), defineAwsServiceDashboard(), ...apis])` and mount the construct on a `Stack`. Tests:
   - Synth with `defineApi('orders')` and `defineApi('users')`, then again with `defineApi('billing')` inserted between them. Pull `template.findResources('AWS::CloudWatch::AnomalyDetector')` from both and assert the logical id of the detector whose `Dimensions` `FunctionName` value starts with `users-route` is identical across the two synths, and that the second synth has exactly one more lambda detector.
   - Synth with `defineAwsServiceDashboard({ disableAnomalyDetection: true })` and assert zero `AWS::CloudWatch::AnomalyDetector` resources, so the opt-out the reporter is relying on stays covered.
   Run from the repo root with `npx vitest run quidproquo-deploy-awscdk/src/constructs/feature/config/dashboard`.

5. **Call out the one-time migration in the changelog.** Every existing stack has detectors under the old `duration-anomaly-detector-{index}` ids. Deploying the fix renames all of them, and CloudFormation creates the renamed detectors before deleting the old ones, so each new detector collides with the old detector still sitting on the same metric. The upgrade path is: deploy once with `defineAwsServiceDashboard({ disableAnomalyDetection: true })` (deletes the old detectors), then deploy again with it re-enabled. Anyone already running with `disableAnomalyDetection: true`, as the reporter is, needs only the second deploy. Add this under `### Breaking changes` for the release that carries the fix so nobody hits the same `AlreadyExists` rollback on upgrade. A custom resource that deletes before creating was considered and rejected as far more machinery than a one-line upgrade note deserves.

6. **Lint and build** with `npm run lint -w quidproquo-deploy-awscdk` and `npm run build -w quidproquo-deploy-awscdk`.
