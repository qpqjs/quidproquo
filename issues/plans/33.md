# Issue #33: NPM i - audit vulnerabilities

**Verdict:** enhancement
**Status:** planning
**Branch:** `issue-33`

## Summary

`npm audit` currently reports 16 vulnerabilities (12 high, 4 moderate) across the
workspace. The reporter wants these reduced as much as possible without resorting
to `package.json` `overrides` hacks, i.e. by fixing the actual version pins that
pull in the vulnerable transitive packages.

## Affected packages

- `package.json` (root): carries an existing `overrides.adm-zip: ^0.6.0` entry
  that does not actually apply (see below) and a `devDependencies["@module-federation/enhanced"]: "^2.6.0"` range that is being dragged down by exact pins elsewhere.
- `quidproquo-deploy-rspack`, `quidproquo-deploy-webpack`: pin
  `@module-federation/enhanced` at the exact version `2.6.0` and
  `@module-federation/node` at the exact version `2.7.45`. These exact (non-caret)
  pins are why `npm audit fix` needs `--force` to touch `adm-zip` and `undici`:
  npm can't move off the vulnerable nested `adm-zip@0.5.10` / old `@module-federation/node`
  without a version bump these packages don't allow.
- `quidproquo-actionprocessor-awslambda`: same `@module-federation/enhanced: "2.6.0"`
  exact pin, same effect.
- `quidproquo-dev-server`: direct `express: "^4.21.2"` dependency; the flagged `qs`
  vulnerability comes in through `body-parser`/`express`'s own `qs` range and the
  audit output says a plain `npm audit fix` (no `--force`) covers it, so this is
  likely just a lockfile refresh.
- Everything else flagged (`brace-expansion`, `fast-uri`, `js-yaml`, `nanoid`,
  `postcss`) comes in through caret-ranged transitive deps of dev tooling
  (`eslint`/`@eslint/eslintrc` for `js-yaml` and one `brace-expansion` chain,
  `glob`/`minimatch` for the other `brace-expansion` chains, `ajv` for `fast-uri`,
  and the vite/vitest toolchain for `nanoid`/`postcss`). Their ranges already allow
  a patched version, so these should resolve from a plain `npm audit fix` /
  `npm install` lockfile refresh with no manual pin changes.

## Approach

1. Run `npm audit fix` (no `--force`) at the repo root and commit the resulting
   `package-lock.json` changes. This should clear `brace-expansion`, `fast-uri`,
   `js-yaml`, `nanoid`, `postcss`, and `qs`/`express`/`body-parser` per the audit
   output, since all of those sit behind caret ranges.
2. Bump the exact `@module-federation/enhanced` and `@module-federation/node`
   pins in `quidproquo-deploy-rspack/package.json`,
   `quidproquo-deploy-webpack/package.json`, and
   `quidproquo-actionprocessor-awslambda/package.json` (and the root
   `devDependencies` range) to the newest versions that satisfy the module
   federation build. Target versions that ship non-vulnerable `adm-zip`
   (>=0.6.0) and `undici` (>=7.28.1, or whatever the fixed line turns out to be)
   as direct/nested deps, so the fix comes from a genuine version bump instead of
   `--force` or an override. A breaking major bump is acceptable here: nothing
   outside this library consumes the module federation setup, so it only needs
   to keep working internally.
3. Once step 2 lands a real fix for `adm-zip`, remove the now-redundant
   `overrides.adm-zip` entry from root `package.json` (it currently resolves to
   `0.5.10` in the nested `@module-federation` trees anyway, so it isn't doing
   anything today) and drop the `overrides` block down to just the
   `react-d3-tree` / `uuid` entry, or remove it entirely if that one is also no
   longer needed.
4. After the version bumps, run the module federation build path
   (`quidproquo-deploy-rspack`, `quidproquo-deploy-webpack`, the AWS Lambda
   action processor) and the existing test suites to confirm nothing broke, then
   run `npm audit` again and record in this plan (or the PR description) which
   of the original 16 findings remain and why (e.g. no non-breaking fix exists
   yet upstream). A fully green audit is not the bar for this pass; findings
   with no non-`--force`, non-override fix available can be left and documented.
5. Separately verify quidproquojs.com still builds/deploys correctly after the
   dependency bumps, since it's the other consumer of this deploy tooling.
