# Issue #36: query string support

**Verdict:** enhancement
**Status:** in-progress
**Branch:** `issue-36`

## Summary

SEO stories run from the CloudFront origin-request Lambda@Edge never see the request's query string: the record builder hard-codes `query: {}`, and the CDK behaviour for SEO paths does not forward query strings to the origin anyway. API routes are not affected: API Gateway already supplies `queryStringParameters` / `multiValueQueryStringParameters` and the dev server proxy already passes express's `req.query`. The fix is to populate `SeoEvent.query` on AWS and to make the dev server's api query shape match production. Running SEO stories from the dev server is out of scope (it is a federated frontend dev server today) and would be its own issue.

## Affected packages

- `quidproquo-webserver`: owns the `SeoEvent` / `HTTPEvent` query shape and the shared HTTP event utils; the new query-string parser belongs here so every runtime produces the same shape.
- `quidproquo-actionprocessor-awslambda`: `cloudFrontOriginRequest/getEventGetRecordsActionProcessor.ts` is where the `TODO: query string support` lives and where `cf.request.querystring` needs parsing.
- `quidproquo-deploy-awscdk`: `WebQpqWebserverWebEntryConstruct.ts` adds the SEO behaviours with no origin request policy, so CloudFront strips the query string before the origin-request event fires. `QpqWebServerCacheConstruct.ts` builds the cache policy with no query string behaviour, so cached SEO responses would ignore the query.
- `quidproquo-dev-server`: `apiImplementation.ts` already passes express's `req.query`, but with express's extended parser (`qs`) the shape differs from API Gateway. There is no SEO / origin-request path in the dev server at all, and adding one is out of scope for this issue.

## Approach

1. **Name the query shape.** In `quidproquo-webserver/src/types/HTTPEvent.ts` add `export type HttpEventQuery = { [key: string]: undefined | string | string[] };` and use it for `HTTPEvent.query`. Repoint `SeoEvent.query` in `quidproquo-webserver/src/types/SEOEvent.ts` and `ExpressEvent.query` in `quidproquo-dev-server/src/types/ExpressEvent.ts` to the same type. Also use it for the `as` cast in `quidproquo-actionprocessor-awslambda/src/getActionProcessor/core/event/apiGatwayEvent/api/getEventGetRecordsActionProcessor.ts`. `HTTPEvent.ts` is already exported through the `types` barrel, so nothing else changes.

2. **Add a shared parser.** New file `quidproquo-webserver/src/utils/queryStringUtils.ts` exporting `parseQueryString(rawQueryString: string): HttpEventQuery`. Build it on `URLSearchParams` (available on Node 22, which is the Lambda@Edge runtime the CDK pins): strip a leading `?` if present, decode keys and values, a key seen once becomes a `string`, a key seen more than once becomes a `string[]` (same convention `readUriQueryParamFromEvent` in `httpEventUtils.ts` already expects), and `''` returns `{}`. Export it from `quidproquo-webserver/src/utils/index.ts` so it reaches `qpqWebServerUtils`. Add `queryStringUtils.test.ts` next to it covering: empty string, single key, repeated key, percent-encoded and `+` values, a key with no value (`?flag` gives `flag: ''`), and a leading `?`.

3. **Populate the SEO record on AWS.** In `quidproquo-actionprocessor-awslambda/src/getActionProcessor/core/event/cloudFrontOriginRequest/getEventGetRecordsActionProcessor.ts` replace the `// TODO: query string support` / `query: {}` lines with `query: qpqWebServerUtils.parseQueryString(cfRecordRequest.querystring)`. `CloudFrontRequest.querystring` (from `@types/aws-lambda`) is a plain string and is `''` when absent, so no null guard is needed. Update `cloudFrontOriginRequest.test.ts`: give `buildCloudFrontRequest` an optional `querystring` argument (defaulting to `''`), keep the existing `query: {}` assertion for the no-query case, and add a case such as `'a=1&tag=x&tag=y'` asserting `{ a: '1', tag: ['x', 'y'] }`.

4. **Forward the query string to the origin.** In `quidproquo-deploy-awscdk/src/constructs/feature/webserver/webEntry/WebQpqWebserverWebEntryConstruct.ts`, the `distribution.addBehavior(wildcardPath, ...)` call inside the `for (let seo of seos)` loop has no `originRequestPolicy`, and the default `cachePolicy` is `CACHING_DISABLED`. With that combination CloudFront drops query strings before the origin-request event, so step 3 would still see `''` in production. Add `originRequestPolicy: aws_cloudfront.OriginRequestPolicy.ALL_VIEWER_EXCEPT_HOST_HEADER` to that behaviour. It is an AWS managed policy, so it costs no new resource against the account's origin-request-policy limit (the file already carries a comment about the cache policy limit), it forwards every query string and header, and it leaves the Host header alone so the S3 origin still resolves. Do not use `ALL_VIEWER`; forwarding Host breaks S3 origins.

5. **Include the query string in the SEO cache key.** In `quidproquo-deploy-awscdk/src/constructs/feature/webserver/cache/QpqWebServerCacheConstruct.ts` the `CachePolicy` sets `headerBehavior` but no `queryStringBehavior`, so it defaults to none. Once SEO stories vary output by query, a cached `/page?a=1` would be served for `/page?a=2`. Add `queryStringBehavior: aws_cloudfront.CacheQueryStringBehavior.all()`. This policy is also used by web entries and their `ignoreCache` behaviours, where including the query in the key is what cache-busting `?v=` params expect anyway. The maintainer confirmed this is fine as the default for every `defineCache` policy, so do not add a `CacheSettings` option; if a per-cache opt-out is ever needed it can be added later as `queryStringBehavior?: 'all' | 'none'` on `CacheSettings` rather than a second cache policy.

6. **Make the dev server produce the same shape.** In `quidproquo-dev-server/src/implementations/apiImplementation.ts` the proxy handler builds `ExpressEvent.query` from `req.query`. Express 4's default `extended` parser turns `a[b]=1` into nested objects and `a[]=1` into arrays, which the `HttpEventQuery` type does not describe and API Gateway never produces. Replace it with `qpqWebServerUtils.parseQueryString(req.url.split('?')[1] ?? '')` (the handler already splits `req.url` on `?` for `path`; pull the split into one `const [rawPath, rawQueryString = '']` above the event literal so it is done once). `quidproquo-dev-server/src/actionProcessor/core/event/express/api/getEventGetRecordsActionProcessor.ts` passes `expressEvent.query` straight through and needs no change. Add a test in `apiImplementation` coverage or the express `getEventGetRecordsActionProcessor.test.ts` asserting a repeated key arrives as `string[]`.

7. **Docs.** In `quidproquojs.com/docusaurus/docs/config/webserver/seo.md`, the "On AWS" bullet describes the two edge functions and the per-route behaviour; add a sentence that the behaviour forwards the viewer's query string to the origin-request function and that the story receives it parsed as `SeoEvent.query` (single value as a string, repeated keys as an array). In `quidproquojs.com/docusaurus/docs/config/webserver/cache.md`, the "On AWS" bullet lists what the cache policy keys on (the header allow-list, gzip, brotli); add that the full query string is part of the cache key. Follow the writing style rules in `CLAUDE.md` (no em dashes) for the new sentences even though the surrounding text predates them.

8. **Verify.** Run `npm run test -w quidproquo-webserver`, `npm run test -w quidproquo-actionprocessor-awslambda`, `npm run test -w quidproquo-dev-server`, then `npm run lint` and `npm run build -w quidproquo-deploy-awscdk` (the CDK package is the one most likely to fail typing on the enum names).
