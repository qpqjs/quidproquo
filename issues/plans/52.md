# Issue #52: AI prompt: cache points are not moved along the tool loop, so each step re-pays for earlier tool results

**Verdict:** enhancement
**Status:** ready
**Branch:** `issue-52`

## Summary

The two Bedrock prompt processors place cache points once, before the SDK call, so every step of the SDK's tool loop re-sends the tool calls and results added by earlier steps at full input price. The ask is to move a cache point onto the newest message on each step via `prepareStep`, and to log cache usage for every step (not just the last) so the saving can be seen in CloudWatch.

## Affected packages

- `quidproquo-actionprocessor-awslambda`: owns the two processors and the cache-point helpers under `src/getActionProcessor/core/ai/`. All the code changes land here.
- `quidproquo-core`: no change. `caching`, `maxSteps` and `maxDurationMs` on `AskAiPromptOptions` already carry everything the processor needs.
- `quidproquojs.com`: one-line doc tweak for the `caching` option.

## Approach

How the pieces fit today, in `quidproquo-actionprocessor-awslambda/src/getActionProcessor/core/ai/`:

- `getAiPromptStreamActionProcessor.ts` and `getAiPromptActionProcessor.ts` build the call the same way: `toCacheableSystem(payload.system, payload.caching)` for `system`, `toCacheableMessages(await toSdkMessages(...), payload.caching)` for `messages`, `stopWhen: buildAiStopConditions(payload)`, then `streamText` / `generateText`. The SDK runs the whole tool loop inside that one call.
- `logic/toCacheableMessages.ts` puts a `bedrock.cachePoint` on the newest two messages (the second-to-last is the one a resumed round re-sends byte-identically; see its comment). `logic/toCacheableSystem.ts` shapes `system` as a `SystemModelMessage` with a cache point. That is three of Bedrock's four cache points per request, leaving one free for a moving point.
- Cache usage is logged once from `finalStep.usage.inputTokenDetails` (the stream processor awaits `finalStep` after draining `fullStream`, wrapped in a try/catch because `finalStep` rejects when the stream errored before completing a step).

Steps:

1. **Add `logic/toCacheableStepMessages.ts`** (pure helper, one export, plus `toCacheableStepMessages.test.ts`). Signature: `(messages: ModelMessage[]) => ModelMessage[]`. It returns a copy of the array with a `bedrock: { cachePoint: { type: 'default' } }` merged into the last message's `providerOptions`, preserving any other `providerOptions` keys. Move the existing private `withCachePoint` out of `toCacheableMessages.ts` into its own file `logic/withCachePoint.ts` so both helpers share it (one export per file; both import it directly, not via the barrel). Empty input returns the input unchanged. Tests: lone message gets the point, only the last of several gets it, existing `providerOptions` are merged not overwritten, empty array passes through.

2. **Add `logic/buildAiPrepareStep.ts`** (plus test). Signature: `(caching: boolean | undefined) => PrepareStepFunction<ToolSet> | undefined` (type from `ai`; check the installed `ai` 7.x `index.d.ts` for the exact name, it is `PrepareStepFunction` in 5.x and 6.x and takes `{ steps, stepNumber, model, messages }`, returning `{ model?, toolChoice?, activeTools?, system?, messages? } | undefined`). Returns `undefined` when caching is off so the SDK call is byte-identical to today. When caching is on, the returned function:
   - returns `undefined` on `stepNumber === 0`, because the initial messages already carry the points from `toCacheableMessages` and the prompt-only path has nothing to cache yet;
   - on any later step returns `{ messages: toCacheableStepMessages(messages) }`. The SDK rebuilds `messages` for each step as the initial messages followed by the response messages of the steps so far, and only reads `providerOptions` off the array the function returns, so the moving point never accumulates: step N's point lives only on the copy handed to step N, and step N+1 places its own on its new last message. The last message on a step > 0 is always a tool-result message appended by the loop (the loop only continues after tool calls), so it never collides with the two durable points. Do not return `system`; leaving it out keeps the `SystemModelMessage` cache point from `toCacheableSystem`.
   - Budget check for the JSDoc: system (1) + two durable message points (2) + the moving one (1) = Bedrock's limit of four. Note that Bedrock silently ignores a checkpoint under its minimum token size (1024 for most Anthropic models), so a small tool result just does not cache; it does not error.
   - Tests: `undefined` when caching is false/undefined; step 0 returns `undefined`; step 1 with `[user, assistant(tool-call), tool(result)]` returns only the tool message changed; `system` is absent from the result; `steps`/`model` are ignored.

3. **Add `logic/buildAiStepUsageLogger.ts`** (plus test). Signature: `(caching: boolean | undefined) => ((step: StepResult<ToolSet>) => void) | undefined`. Returns `undefined` when caching is off (today nothing is logged in that case; keep that). When on, it returns an `onStepFinish` callback that keeps a step counter in its closure and logs `console.log('AI prompt cache usage:', { step: n, ...step.usage?.inputTokenDetails })` (or two args, `('AI prompt cache usage:', n, step.usage?.inputTokenDetails)`; either is fine, pick one and match it in the tests). The `inputTokenDetails` shape (`noCacheTokens`, `cacheReadTokens`, `cacheWriteTokens`) is what the existing processor tests already assert on. Tests: `undefined` when off; two invocations log step 0 then step 1 with their details; a step with no `usage` logs `undefined` details rather than throwing.

4. **Wire both into `getAiPromptStreamActionProcessor.ts`.** Add `prepareStep: buildAiPrepareStep(payload.caching)` and `onStepFinish: buildAiStepUsageLogger(payload.caching)` to the `streamText` options. Delete the `finalStep` destructure, the post-drain `if (payload.caching) { try { await finalStep ... } }` block inside `aiStreamIterator`, and the `toErrorMessage` import if nothing else in the file uses it (it is only used there). The comment about `providerMetadata.bedrock.usage` not carrying `cacheReadInputTokens` moves to `buildAiStepUsageLogger.ts`, since that is now where `usage.inputTokenDetails` is read. No comment should describe the old `finalStep` approach.

5. **Wire both into `getAiPromptActionProcessor.ts`** the same way on `generateText`, and delete the `if (payload.caching) console.log(... result.finalStep ...)` block after the call.

6. **Update `logic/toCacheableMessages.ts`'s comment** so it describes the full set as it is now: system point from `toCacheableSystem`, two durable points here, moving per-step point from `buildAiPrepareStep`. Reword, do not add a "previously" sentence. Export the new helpers from `logic/index.ts` (alphabetical, matching the file).

7. **Update the processor tests.** `getAiPromptStreamActionProcessor.test.ts` and `getAiPromptActionProcessor.test.ts` mock `./logic` wholesale, so add `buildAiPrepareStep: vi.fn(() => undefined)` and `buildAiStepUsageLogger: vi.fn(() => undefined)` to each mock factory. Replace the two `finalStep` logging tests in each file with: `buildAiPrepareStep` and `buildAiStepUsageLogger` are called with `payload.caching`, and whatever they return is passed through as `prepareStep` / `onStepFinish` on the SDK call (use `expect.objectContaining`). The "does not log cache usage when caching is off" cases become "passes `undefined` through when caching is off". In the stream test, also assert the iterator still drains cleanly with no `finalStep` on the mocked return (it already omits it in most cases).

8. **Docs and changelog.** In `quidproquojs.com/docusaurus/docs/actions/core/ai/ask-ai-prompt.md`, extend the `caching` row (line 52) to say the processor also moves a cache point along the tool loop so each step reads the previous step's prefix from cache. Add a line to the top `## 0.1.29` section of `CHANGELOG.md` prefixed `actionprocessor-awslambda:` describing the moving cache point and the per-step `AI prompt cache usage:` log.

9. **Verify.** `npm run test -w quidproquo-actionprocessor-awslambda` and `npm run lint`. For a real-world check, run an assistant chat through `defineEventDocAi` (it calls `askAiPromptStream` with `caching: true` from `quidproquo-features/src/eventDocAi/logic/askEventDocAiStreamTurn.ts`) with a tool that returns a result over ~1k tokens and confirm step 1 onwards shows `cacheReadTokens` roughly equal to step 0's total input in the CloudWatch log lines.

Things to double-check while implementing, since `node_modules` was not available when this plan was written:

- The exact `prepareStep` and `onStepFinish` option names and types on `ai` 7.x (`PrepareStepFunction`, `StepResult`, `LanguageModelUsage.inputTokenDetails`). Both options exist on `generateText` and `streamText` since `ai` 5.
- That `@ai-sdk/amazon-bedrock` 5.x emits a `cachePoint` content block for `providerOptions.bedrock.cachePoint` on a `tool`-role message, not just `user`/`assistant`. It does in current releases (it reads the same `providerOptions` off every message in its message converter); if a given version does not, fall back to placing the moving point on the newest assistant message instead and say so in the helper's JSDoc.

## Open questions

None. The reporter's two asks map directly onto `prepareStep` and `onStepFinish`, and the four-point budget works out as described.
