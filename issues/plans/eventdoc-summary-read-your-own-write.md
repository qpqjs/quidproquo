# EventDoc: the summary row reads its own lifecycle write

**Verdict:** bug
**Status:** in-progress (implemented on `main`, uncommitted, awaiting Joe's review)
**Branch:** `eventdoc-summary-sync` (no GitHub issue yet; reported by Harry on Slack, 14 Oct 2026, worked around in doccypoccy under #765 and #1267)

## Summary

For a few seconds after a publish, archive, restore, rename or recode, the EventDoc summary row still describes the document as it was before. Every reader that takes the row at face value answers wrong in that window, and the one that matters most, "which published version is in effect now", runs the previous version. The fix is for the seven reserved lifecycle events to write the summary row before their append returns, with a watermark and conditional writes so neither the request path nor the stream projector can move the row backwards. Domain edits stay on the projector as they are today.

## Background

The summary row (`type`, `id`, `code`, `name`, `createdAt`, `updatedAt`, `deletedAt`, `versions[]`) is a read model. It is written by two things only:

- `askEventDocCreate` applies the InitState event to the summary in-process and upserts the row before returning (`packages/features/src/eventDoc/logic/askEventDocCreate.ts`).
- The events-store stream handler `projectEventDocSummary` (`packages/features/src/eventDoc/entry/kvsStream/eventDocSummaryProjector.ts`) rebuilds it after every append, through `askEventDocProjectAtEvent`, which folds the snapshot views and writes the summary and a snapshot per view.

Deployed, the stream is a DynamoDB stream feeding a Lambda with a 100 record batch and a 5 second batching window (`packages/deploy-awscdk/src/constructs/feature/core/keyValueStore/QpqApiCoreKeyValueStoreStreamConstruct.ts`), so the row trails an append by up to 5 seconds plus an invocation. Locally the dev server emits the record onto an in-process bus without waiting for the handler, so the lag is milliseconds and the bug is invisible in local testing.

The append itself does not touch the row: `askEventDocEventAppend` says so in its doc comment. So after a Publish, `askEventDocPublishedVersionAsOf` reads a row whose `versions[]` has no `publishedAt` on the new version and resolves the previous one. The same row feeds `askEventDocGetById`, the list reads, the code lookups, the draft pointer, the summary handed to the onPublish and onAppend hooks, the return value of soft delete and restore, and the `GET /{id}` route. All of them are stale in the window.

Measured on 12 Oct 2026 in Kiln: 8 of 146 live flow runs started 0.3 to 3.6 seconds after a publish and ran the version before it. A first publish answered 404. An app client published with narrower grants issued a token under the old grants. An Inbox refused a sender it had just been told to trust.

Snapshots are not affected in the same way. Every snapshot read in the framework is a fold seed, never the answer: the document-state reads and the client bootstrap take the newest snapshot at or before the target and fold the gap forward from the log. A stale snapshot only means a longer fold. The summary is the one projection served raw, which is why the fix is on the summary writers and nowhere else.

Harry's workaround lives in doccypoccy at `apps/docgen/packages/service-utils/src/qpq-features/eventDocAtHead/` with an entry in `qpq-uplifts.md`. It reads the row, then the log head with a consistent read, and projects the summary in memory when the log is ahead. Correct, but it is a copy of the projector that will drift, it costs a consistent read per resolve and one per document on list pages, and it cannot fix the row itself. This plan replaces it.

## Affected packages

- `@qpqjs/core`: the key-value Update action gains a write condition and a `ConditionFailed` error type.
- `@qpqjs/actionprocessor-aws`: `updateItem` sends the condition as a DynamoDB ConditionExpression and maps the failure.
- `@qpqjs/dev-server`: the sqlite repository evaluates the condition inside its update transaction; contract tests cover both engines.
- `@qpqjs/features`: the summary row gets a `headEventId` watermark, every summary write is conditional, reserved appends project synchronously, the published-version resolver folds with a consistent read, and the tests.
- doccypoccy (follow-up, other repo): remove the at-head workaround once this ships.

## Approach

The shape in one paragraph. The summary view carries `eventId`, the event it is folded through, set by the summary reducer on every event. After a reserved event's write succeeds, the append refolds the row in process: read the stored row, apply the events after it up to the new one with the summary reducer, write, then run the hooks with that summary and return. No projection, no dynamic-function call, no snapshot writes. Every summary write, from the request path or the projector, carries the condition "no `eventId` yet, or stored `eventId` below the view's", so a late stream batch or a concurrent publish cannot regress the row. The projector keeps its job for domain events and snapshots. Readers change in one place: the published-version resolver folds its state with a consistent read, because the head it resolves was written moments earlier.

Steps 1 to 5 ship on their own with no behaviour change beyond the ordering guard. Steps 6 to 9 are the fix.

### Conditional Update (core and the two runtimes)

1. `packages/core/src/actions/keyValueStore/askKeyValueStoreUpdate.ts`: add `condition?: KvsQueryOperation` to `KeyValueStoreUpdateOptions`, evaluated against the item as stored before the update; when it is false nothing is written. Add `'ConditionFailed'` to `errorTypes`, with a comment saying it is the condition losing, distinct from Upsert's `Conflict`, so a caller can treat it as "someone newer already wrote". No new operators: `KvsQueryOperationType` already has `NotExists` and `LessThan`, and `kvsOr`, `kvsNotExists`, `kvsLessThan` exist in the helpers. Only two runtimes implement Update, the Lambda processor and the dev server.
2. `packages/actionprocessor-aws/src/logic/dynamo/updateItem.ts`: accept the condition and set `ConditionExpression` with `buildDynamoQueryExpression` (`logic/dynamo/qpqDynamoOrm/buildDynamoQueryExpression.ts`, the builder `scan.ts` uses for its filter), merging its attribute names and values with the update's. Check the placeholder names the two builders generate cannot collide; prefix one side if they can. `getActionProcessor/core/keyValueStore/getKeyValueStoreUpdateActionProcessor.ts`: pass `options?.condition` through the scoped translator for parity with `scoped.update(updates)`, and map `ConditionalCheckFailedException` to `askKeyValueStoreUpdateBase.errorType.ConditionFailed`. Extend `getKeyValueStoreUpdateActionProcessor.test.ts`.
3. `packages/dev-server/src/logic/keyValueStore/KvsRepository.ts`: `update` takes `options?: { condition?: KvsQueryOperation }`. `SqliteKvsRepository.ts` `update`: validate with `validateKvsQueryOperation` up front, and inside `runInImmediateTransaction`, after `selectRowData`, evaluate `evaluateKvsQueryOperation(currentItem, condition, storeConfig)` and throw `ConditionalCheckFailedException` when false. A missing row evaluates against the key-only base item, which matches DynamoDB, where attribute-not-exists is true for an absent item. `actionProcessor/core/keyValueStore/getKeyValueStoreUpdateActionProcessor.ts`: pass the condition, map the exception to `ConditionFailed`, and skip the stream emission on failure because nothing was written. `kvsRepositoryContractTests.ts`: a condition that holds applies the update; one that fails throws and leaves the row as it was.

### The view's eventId and guarded summary writes (@qpqjs/features)

4. `packages/features/src/eventDoc/models/EventDocSummary.ts`: `eventDocSummaryViewSchema` gains a required `eventId: z.number()`, the event the view is folded through (a version's own `eventId` is that version's head). `summary/applyEventDocSummaryEvent.ts` sets it on every event it applies, next to the tail version's `eventId`, and `summary/createEventDocSummarySeed.ts` seeds it at -1. The stored row adds nothing: `type` stays the only persistence-time field. A row written before the field existed has no `eventId`, which the writers treat as older than anything. A breaking type change for code that builds a summary by hand; logged in `breaking-changes.md`.
5. `packages/features/src/eventDoc/data/askEventDocSummaryViewWrite.ts`: add `kvsSet('eventId', view.eventId)`, pass `condition: kvsOr([kvsNotExists('eventId'), kvsLessThan('eventId', view.eventId)])`, wrap the update in `askCatch`, and return `false` on `ConditionFailed` (a newer row is stored) and `true` otherwise; rethrow anything else. `logic/askEventDocProjectAtEvent.ts` returns the summary view it wrote (null when the log was empty) and parses the summary view it is about to write with `eventDocSummaryViewSchema`, falling back to the rederive path when it does not parse (a snapshot from before the field existed, or a fold that assembles something else), so no cast trusts stored or folded data. `logic/askEventDocSummaryRederive.ts` returns the view it wrote. `askEventDocCreate` and the transfer import's `askEventDocWriteForeignEvents` keep their unconditional puts: the row cannot exist before its InitState, and an import may have rewritten the log, which is the one case the row must be allowed to move backwards. Snapshots are still written when the summary write is refused: a snapshot is a per-event row and readers take the newest at or before their target, so an older one cannot regress anything.

### Refold on reserved appends

6. `packages/features/src/eventDoc/logic/isEventDocReservedEffect.ts` (new, pure): true for the seven values of `EventDocEffect`, which are exactly the event types the summary reducer handles (`summary/eventDocSummaryReducer.ts`). Test alongside.
7. `packages/features/src/eventDoc/logic/askEventDocSummaryRefold.ts` (new): `(modelId, eventId) => AskResponse<Nullable<EventDocSummary>>`. Read the row with a consistent read (`askEventDocGetById` gains a `consistentRead` option and reads through `askKeyValueStoreQuery` with limit 1). A row at or past the event is returned as it is. Otherwise read the events after the row's `eventId` up to the new one with a consistent read and apply them with `applyEventDocSummaryEvent`; a row with no `eventId` is refolded from the whole log with `foldEventDocSummary`. Write through `askEventDocSummaryViewWrite`. The whole refold runs under `askCatch`: a failure is logged at warning with `askLogCreate` and null is returned, because the event is already durable, a client retry of a failed append would double-append, and the projector repairs the row within its window. No dynamic-function call and no snapshot I/O on this path; the only acceptance gap is a server-authored lifecycle event appended with validation off that the fold would reject, which the raw-log rederive fallback already has today.
8. `packages/features/src/eventDoc/logic/askEventDocEventAppend.ts`: after `const event = result.result;` and before the hooks, `const refolded = isEventDocReservedEffect(event.type) ? yield* askEventDocSummaryRefold(modelId, event.payload.metadata.eventId) : null;`. Hand `refolded ?? (yield* askEventDocGetByIdOrThrow(modelId))` to onPublish and onAppend, so a hook on a lifecycle event sees the row it expects. Rewrite the function's doc comment: domain events leave the summary to the stream projector; a reserved lifecycle event brings it up to date here before returning. `logic/askEventDocAppendServerEvents.ts`: after the retry succeeds, if any event in the batch is reserved, run `askEventDocSummaryRefold` at the batch's last event id. The batch already refuses Publish and hook stores, so this covers SetName, SetCode, Delete, Restore and CreateDraft in a batch.
9. `packages/features/src/eventDoc/logic/askEventDocPublishedVersionAsOf.ts`: pass `{ consistentRead: true }` to `askEventDocDocumentStateAsOf`. The version head it resolves is usually the Publish event written moments before by the same user's next request, and an eventually consistent gap read can fold short of it. Single-partition, small query. Add the reason to the doc comment.

### Tests

10. `packages/features/src/eventDoc/logic/askEventDocEventAppend.test.ts` (new, `runStory` with mocks by action type): a Publish append issues the summary Update with `publishedAt` on the new version, `eventId` equal to the Publish event id and the condition, before the story returns, writing no snapshots and calling no dynamic function; a Delete append writes `deletedAt`; the refold carries the row through events the projector has not folded yet; a row with no `eventId` is refolded from the whole log; a row already past the event is left alone; the hooks receive the refolded summary after the write; a domain append issues no summary write; a failed write logs and the append still returns the event.
11. `packages/features/src/eventDoc/logic/askEventDocProjectAtEvent.test.ts` (new): the summary write carries the view's `eventId`; a `ConditionFailed` on it is swallowed and the snapshots are still written; the seed-at-event branch writes the seed's view without folding, and rederives from the log for a seed view that does not parse, as one from before the field existed.
12. `packages/features/src/eventDoc/logic/askEventDocPublishedVersionAsOf.test.ts`: assert the gap read is consistent. Add Harry's window fixture (events store holds the Publish, summary row does not) as the case that documents why the fix is on the write side: with the row behind, the resolver alone still answers the old version.
13. `packages/features/src/eventDoc/logic/isEventDocReservedEffect.test.ts`, the Lambda processor test from step 2, the dev-server contract cases from step 3.
14. Run the four packages' suites and `npm run lint`. Confirm the dev server still projects on the bus by publishing a doc on `@qpqjs/dev-server` and reading `GET /{id}` immediately.

### Release and follow-up

15. Not a breaking change: an optional field on the stored row and an optional option on Update. Rows without a watermark need no migration; absence counts as older and the first write stamps it. Changelog entry through the `changes` skill at release.
16. doccypoccy, after the bump lands on `harry-kiln`: delete `apps/docgen/packages/service-utils/src/qpq-features/eventDocAtHead/`, swap the template, pack, transformer, view, Inbox and app-client call sites back to `createEventDocBackend(definition).askPublishedVersionAsOf`, repoint the `askEventDocSummaryAtHead` imports to `askEventDocGetById`, and delete the uplift section. Keep the `consistentRead: true` Harry added in `askEventDocVersionList`; it is harmless. Keep his four window tests in spirit: they become the vitest cases in steps 10 to 12.

## Open questions

- [ ] Branch and issue: create a GitHub issue so the plan follows the `issue-{n}` convention, or keep the slug.
- [ ] Publish latency budget. The synchronous projection adds a snapshot seed read (blob reads from the storage drive for states over the inline limit), a consistent gap read, one dynamic-function fold and the writes. Measure one deployed publish on a large flow. If it bites, the optimisation is the in-process incremental apply that `askEventDocCreate` already does for InitState: read the row consistently, and when its watermark is the previous event, apply the one event with `applyEventDocSummaryEvent` and write conditionally; otherwise fall back to the full projection. That path needs the fold's acceptance check for server-authored events first.
- [ ] Domain appends. Stamping `updatedAt`, `updatedBy` and `headEventId` on every append is one conditional update with no fold, and the watermark makes it safe. Deferred: it is the burst coalescing the projector exists for, and a busy editor would hit one row on every save. Revisit if list ordering lag is reported.
- [ ] An opt-in at-head check on `askEventDocGetById` for hot authorisation paths (token issuance). Deferred unless Harry wants belt and braces; with the row written in the request, the only remaining staleness is domain-event `updatedAt` and the logged failure case.
