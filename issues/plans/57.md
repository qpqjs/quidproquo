# Issue #57: EventDoc: the effective published version is read from an asynchronously projected summary, so reads just after Publish return the previous version

**Verdict:** bug
**Status:** ready
**Branch:** `issue-57`

## Summary

`askEventDocEventAppend` writes a Publish event and returns, leaving the summary row (where `versions[].effectiveFrom` lives) to the events-store stream projector. Until that runs, `askEventDocPublishedVersionAsOf` resolves the previous version (or nothing on a first publish), and the `onPublish` hook is handed a summary that predates the publish. The fix is to run the same projection inline, at the publish event, before the append returns, and to hand the hooks the summary it just wrote. A `consistentRead` option on the published-version read covers callers who need a hard guarantee on the summary row itself.

## Affected packages

- `quidproquo-features`: everything lives under `src/eventDoc/`. `logic/askEventDocEventAppend.ts` is the publish path; `logic/askEventDocProjectAtEvent.ts` and `logic/askEventDocSummaryRederive.ts` are the projection the stream handler (`entry/kvsStream/eventDocSummaryProjector.ts`) already runs and which the append will now run too; `logic/askEventDocPublishedVersionAsOf.ts` and `data/askEventDocGetById.ts` are the read side; `backend/createEventDocBackend.ts` surfaces the read.
- `quidproquojs.com` (docs): `docs/actions/features/event-doc/ask-event-doc-event-append.md`, `docs/actions/features/event-doc/ask-event-doc-get-draft.md`, `docs/config/features/event-doc-routes.md` and `docs/config/features/event-doc-summary.md` all state that nothing on the append path writes the summary. That stops being true for Publish.

No change in `quidproquo-core`: `askKeyValueStoreQuery` already takes `consistentRead`, and `askKeyValueStoreUpdate` is used as-is.

## Approach

Why it happens. `askEventDocEventAppend` (`logic/askEventDocEventAppend.ts`) writes the event with `askEventDocEventWrite` and never touches the summary store; its JSDoc says so. The summary row is rewritten by `projectEventDocSummary` when the events store's stream delivers, which the reporter measured at 0.3 to 3.6 s. `askEventDocPublishedVersionAsOf` reads that row through `askEventDocGetById` (an eventually consistent `askKeyValueStoreQuerySingle`) and picks a version with `effectiveAsOf`, so for the whole lag it sees `versions[]` without the publish stamp. The hook block at the bottom of the append reads the same row with `askEventDocGetByIdOrThrow`, so `onPublish` has the same gap.

Shape of the fix. Publish is rare next to reads and is already special in the append (own hook, rejected by `askEventDocAppendServerEvents`), so the summary is brought up to date inside the publish append rather than on every read. The projection runs at the publish event's own id, which the append has in hand, rather than at a freshly read head as the triage comment on #49 suggested. That saves the consistent head read, and it files the snapshot set at exactly the published version's head, which is the prefix `askEventDocPublishedVersionAsOf` folds (`askEventDocDocumentStateAsOf(id, version.eventId)`), so published renders seed from it directly. If another event landed between the publish write and the projection, the summary is briefly as of the publish rather than head; that event carries its own stream record and the projector moves the summary forward, exactly as for any non-publish append today. The stream projector keeps running after the publish and is idempotent: when it reaches the publish event it finds the snapshot set already there (`seed?.eventId === eventId` in `askEventDocProjectAtEvent`) and only rewrites the summary from the seed.

Steps:

1. **Make the projection return what it wrote.** In `logic/askEventDocSummaryRederive.ts`, pass `{ consistentRead: true }` to `askEventDocEventListAll` and return `Nullable<EventDocSummaryView>`: the view it wrote, or null when the empty log made it delete the row. The consistent read is required here, not optional: on the append path an eventually consistent list can miss the publish event the caller just wrote and rederive a summary without it. (The plan for #49 makes the same consistent-read change for the projector's sake; whichever lands first, the other rebases onto it.) In `logic/askEventDocProjectAtEvent.ts`, return `Nullable<EventDocSummaryView>` as well: the seed's summary on the short-circuit path, the fold's `summaryView` on the main path, and the rederive result on both fallbacks. The stream handler ignores the return value. Update both JSDocs.

2. **Add `logic/askEventDocProjectAppended.ts`.** One story, `askEventDocProjectAppended(modelId: string, eventId: number): AskResponse<Nullable<EventDocSummaryView>>`, that resolves `storeName`/`type` with `askEventDocResolveStore`, builds the functions name with `eventDocFunctionsName(storeName, type)` (the same name `defineEventDoc` registers in the projector's `snapshotFunctions` map, see `config/defineEventDoc.ts` line 18 to 22), and wraps `askEventDocProjectAtEvent(modelId, eventId, functionsName)` in `askCatch`. On an error that `isEventDocFunctionsMissing` recognises, fall back to `askEventDocSummaryRederive(modelId)`; rethrow anything else with `askThrowError`. The fallback matters because `askEventDocProjectAtEvent` calls `foldSnapshotViews` unguarded; the stream handler avoids that by consulting its config map, which the append path does not have. A collection with no registered definition (the setup in `askEventDocOnPublish.test.ts`) must still get its summary rewritten. JSDoc: projects a document at an event this process just wrote, so every log read is consistent; collections with no functions object rederive the summary from the whole log instead. Export it from `logic/index.ts`.

3. **Run it in the publish append.** In `logic/askEventDocEventAppend.ts`, after `const event = result.result;` and before the hook block:

   - Compute `const isPublish = event.type === EventDocEffect.Publish;` and reuse it for `firePublishHook`.
   - When hooks are configured, derive `askEventDocHookStates(modelId, event)` **before** the projection. `askEventDocHookStates` seeds from `askEventDocSnapshotBaseLatest(modelId, eventId, ...)` and, when the base sits exactly at the event, refolds the whole prefix (its own comment explains why). Projecting first would file a snapshot at the publish event and push every publish's hook fold onto that slow path. One inline comment stating that ordering constraint.
   - If `isPublish`, `const projected = yield* askEventDocProjectAppended(modelId, event.payload.metadata.eventId);`. A failure here propagates, matching how hook failures are treated: the event has landed, the caller learns the summary may be stale, and a retried publish is safe (the fold drops the duplicate `clientMessageId`).
   - The `summary` handed to `onPublish`/`onAppend` becomes `projected ? { ...projected, type } : yield* askEventDocGetByIdOrThrow(modelId)`, with `type` from `askEventDocStoreRead` (the same construction `askEventDocCreate` uses). Building it from the projection result rather than re-reading avoids an eventually consistent query that could still return the pre-publish row a few milliseconds after the write. Non-publish appends keep the `askEventDocGetByIdOrThrow` read.
   - Rewrite the function's JSDoc: a Publish append projects the summary row and snapshot set at the publish event before returning; every other append leaves the summary to the stream projector. Remove the sentence saying the summary is never maintained here.

   `askEventDocAppendServerEvents` already rejects Publish events, so it needs no change. `askEventDocReprojectHead` is untouched.

4. **`consistentRead` on the read side.** In `data/askEventDocGetById.ts`, add `options?: { consistentRead?: boolean }` and switch the body from `askKeyValueStoreQuerySingle` to `askKeyValueStoreQuery` with `{ limit: 1, scope, consistentRead: options?.consistentRead }`, returning `page.items[0] ?? null`. The key condition pins both `type` and `id`, so there is exactly one candidate row and the pagination loop in `askKeyValueStoreQuerySingle` was never doing anything; this avoids adding a parameter to a core story. Thread the same `options` through `askEventDocPublishedVersionAsOf(id, clock, options?)` (the summary read only; the event reads inside `askEventDocDocumentStateAsOf` are unchanged) and through `askPublishedVersionAsOf` on `EventDocBackend` and `createEventDocBackend`. Default stays eventually consistent. JSDoc on `askEventDocPublishedVersionAsOf`: after this change a publish is projected before it returns, so the default read sees the new version once the row write has propagated (normally well under a second); pass `consistentRead` when the caller must see a publish it, or another process, completed a moment ago.

5. **Tests.** `npm run test -w quidproquo-features`.

   - `logic/askEventDocOnPublish.test.ts`: in the first test, assert the summary row in `tables[store.storeName]` now carries `versions[0].publishedAt` and `versions[0].effectiveFrom === '2026-07-11T00:00:00.000Z'` straight after the append returns, with no projector run, and that the hook's `payload.summary.versions[0].effectiveFrom` matches. That is the reported bug. Add a test that a non-Publish append issues no Update against the summary store (wrap `createKvsUpdateMock` to count calls per store). In the hook-failure test, assert the summary row is already published even though the hook threw. The existing Query mock supports `Equal`, `GreaterThan` and `LessThanOrEqual` on `sk`, which covers `askEventDocSnapshotSeedLatest` and the whole-log list the rederive issues; the Dynamic Execute mock throws NotFound, so this suite exercises the rederive fallback in step 2.
   - New `logic/askEventDocProjectAppended.test.ts`, built on the `buildMocks` pattern in `entry/kvsStream/eventDocSummaryProjector.spec.ts`: (a) with a registered fold, `foldSnapshotViews` is called once with the prefix up to the given event, the snapshot rows land at that event id, the summary row is written from the fold's `summary` view, and the returned view equals the row written; (b) without a registered fold, the fallback rederives and the returned view matches the row; (c) every events-store Query the story issues carries `consistentRead: true`, including the rederive path.
   - `logic/askEventDocPublishedVersionAsOf.test.ts`: add a case that `{ consistentRead: true }` reaches the summary-store Query action's options, and that the default does not set it.
   - `entry/kvsStream/eventDocSummaryProjector.spec.ts`: no behaviour change, but the `void` return of `askEventDocProjectAtEvent` becomes a value; confirm the suite still passes.

6. **Docs.**

Add `askEventDocProjectAppended` to the "Built from" bullet.

7. **Changelog.** Under the next version in `CHANGELOG.md`: `features: a Publish append projects the document summary and snapshot at the publish event before returning, so askEventDocPublishedVersionAsOf and the onPublish hook see the version just published instead of waiting for the stream projector; askEventDocPublishedVersionAsOf takes an optional consistentRead`. Not a breaking change: new optional parameters only, and `askEventDocProjectAtEvent`/`askEventDocSummaryRederive` gain a return value their existing callers ignore.

8. **Lint and build** with `npm run lint -w quidproquo-features` and `npm run build -w quidproquo-features`.

Known limit, not closed here: the inline projection and the stream projector are no longer serialised per document. If a second writer appends right after the publish and the stream delivers that event fast enough for the projector to write the summary at the newer head before the publish's own summary write lands, the row regresses to the publish's view until the next append. The window is the few tens of milliseconds between the publish write and its summary write, against stream lag the reporter measured at 0.3 s or more. Closing it would need a conditional update on the summary row (a head marker plus a condition on `askKeyValueStoreUpdate`), which is a core change and a separate issue. The Info log line added by #49 records what the projector wrote, so the case is diagnosable if it ever shows up.
