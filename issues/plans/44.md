# Issue #44: KVS: global secondary indexes are unusable on scoped (tenanted) stores; dev server ignores index ordering

**Verdict:** bug
**Status:** ready
**Branch:** `issue-44`

## Summary

On Dynamo the scope prefix is composed into the primary partition key value only, so a scoped query whose key condition names a GSI partition key throws (`queryMissingPartitionKey`), and even if it did not, the index partition would be shared by every tenant. On the dev server the sqlite engine ignores the index entirely: it narrows, orders and pages on the primary `pk`/`sk` columns, so a GSI query with `sortAscending: false` comes back in primary-key order. The fix is to treat every string-typed GSI partition key as a scope-carrying attribute in core, and to make the sqlite read path narrow, order and page by the index keys when a query targets one.

## Affected packages

- `quidproquo-core`: `logic/scope/` composes, strips and validates the scope for exactly one attribute (`scopedKvsTranslator.ts`, `scopedKvsQueryOperation.ts`, `kvsScopeGate.ts`). The index-selection rule that both backends need also belongs here.
- `quidproquo-actionprocessor-awslambda`: the query processor already routes composed conditions to the GSI, but the update, scan-all-scopes and stream-record processors only know about the primary pk, and `getDynamoTableIndexByConfigAndQuery` moves to core.
- `quidproquo-dev-server`: `SqliteKvsRepository.readPage`, `buildKvsKeyNarrowing`, `kvsPageCursor` and the query action processor never consider an index. The contract suite has no index-query cases.
- `quidproquo-features`: no code change, but its GSI-bearing stores (tenant memberships, log stores, event doc summary) are the migration surface.

## Approach

Terminology used below: the **scope-carrying attributes** of a store are its primary partition key plus every `indexes[i].partitionKey.key` that is string-typed and is not also one of the store's primary sort keys. Index sort keys never carry the scope; they are already isolated by living inside a scoped index partition.

The sort-key exclusion exists because the Lambda update and delete processors pass `sortKey` to Dynamo raw (`getKeyValueStoreUpdateActionProcessor.ts` calls `scoped.key(key)` for the pk only). If an attribute that is both primary sort key and GSI partition key were composed on write (tenant memberships: pk `userId`, sk `tenantId`, GSI `tenantId`), every keyed update or delete on the scoped store would miss the row. Such an index stays unscoped and a scoped query on it keeps throwing, exactly as today.

### Core

1. **`quidproquo-core/src/logic/scope/resolveScopeCarryingKvsAttributes.ts`** (new, exported from `logic/scope/index.ts`): `resolveScopeCarryingKvsAttributes(storeConfig, scoped: boolean): { partitionKey: string; indexPartitionKeys: string[] }`. Returns the set defined above. When `scoped` is true, throw `InvalidScopeError` (reuse `validateScopeSupportedForPartitionKeyType`, widen its message to say which attribute) for any index partition key that is number or binary typed and not a primary sort key: a number cannot hold the composed value, so the store cannot be scoped at all, matching the primary-pk rule. When `scoped` is false, skip non-string keys silently (they can never hold a composed value, so the unscoped guard has nothing to check). Every store declaring a GSI today uses string index keys, so nothing existing is rejected.

2. **`quidproquo-core/src/logic/scope/scopedKvsTranslator.ts`**: change `createScopedKvsTranslator(scope, pkAttributeName)` to `createScopedKvsTranslator(scope, pkAttributeName, indexPkAttributeNames: string[] = [])`. Let `scopedAttributes = [pkAttributeName, ...indexPkAttributeNames]`.
   - `key`: unchanged (bare keys are always the primary pk).
   - `item`: compose every attribute in `scopedAttributes` that is present on the item (`!== undefined`); absent index attributes stay absent so sparse GSIs keep working. A present non-string value already throws via `composeScopedKvsValue`.
   - `keyCondition`, `filter`: pass `scopedAttributes` as `pkKeyNames` to `composeScopedKvsQueryOperationOrThrow` / `composeScopedKvsQueryOperation`. These helpers already take an array, so a condition on an index pk now both counts as constraining the scope and gets rewritten.
   - `scanFilter`: the `begins_with` scope predicate stays on the primary pk only (an item always has its pk, so that predicate alone is sufficient and keeps the filter cheap); the rewrite of the caller's filter uses `scopedAttributes`.
   - `strip`: strip every attribute in `scopedAttributes`.
   - Unscoped translator: `guardedItem` validates every scope-carrying attribute; `guardedKeyCondition` passes `scopedAttributes` to `validateUnscopedPkConditionValuesOrThrow`; the scan exclusion stays on the primary pk.
   - Add `update: (updates: KvsUpdate) => KvsUpdate`. Scoped: for each `KvsUpdateAction` whose `attributePath` (string, or single-element array) is a scope-carrying attribute, compose `value` for `Set` and `SetIfNotExists`, leave `Remove` alone, and throw `InvalidScopeError(unsafeCharacters)` for any other action (Add, Delete, Increment cannot apply to a string pk). Unscoped: validate `Set`/`SetIfNotExists` values with `validateRawPkValueForScopeOrThrow`. Without this a scoped `askKeyValueStoreUpdate` that sets an index attribute would write it raw and silently drop the row out of the tenant's index partition.
   - Update the doc comment on `ScopedKvsTranslator` so it describes the attribute set, not "the pk".

3. **`quidproquo-core/src/logic/scope/scopedKvsQueryOperation.ts`**: change `stripScopedKvsItem(scope, item, pkAttributeName)` to take `attributeNames: string[]`; keep the "return the same object when nothing changed" behaviour. Repoint the two tests in `scope.test.ts`.

4. **`quidproquo-core/src/logic/scope/kvsScopeGate.ts`**:
   - `getScopedKvsTranslatorOrThrow`: call `resolveScopeCarryingKvsAttributes(storeConfig, scope !== undefined)` in both branches and pass `indexPartitionKeys` as the new third argument. The unscoped branch keeps passing `''` as the pk when the primary pk is not a string.
   - `resolveScopedPkAttributeOrThrow`: also call the resolver with `scoped: true` so a store the Dynamo backend would reject (number-typed GSI pk) fails on the dev server too. Return type unchanged.
   - Add `validateScopedKvsUpdateOrThrow(qpqConfig, keyValueStoreName, scope, updates)` next to the other validation-only wrappers, delegating to `translator.update`.

5. **Move index selection into core.** Create `quidproquo-core/src/logic/keyValueStore/` with an `index.ts` barrel and one export per file: `isKvsQueryCondition.ts`, `isKvsLogicalOperator.ts`, `flattenKvsQueryConditions.ts`, and `selectKvsQueryIndex.ts` (`(storeConfig, keyCondition) => Nullable<KvsIndex>`, the same rule as today's `getDynamoTableIndexByConfigAndQuery`: primary table wins if the primary pk is named, else the first GSI whose pk is named). Move the existing tests with them. Delete the four originals from `quidproquo-actionprocessor-awslambda/src/logic/dynamo/qpqDynamoOrm/` and repoint the three ORM files that import the guards (`buildExpressionAttributeNames.ts`, `buildExpressionAttributeValues.ts`, `buildDynamoQueryExpression.ts`) to `quidproquo-core`. No re-export shim is left behind. Export the new folder from `quidproquo-core/src/logic/index.ts`.

### Lambda processor

6. **`getKeyValueStoreQueryActionProcessor.ts`**: replace `getDynamoTableIndexByConfigAndQuery(storeConfig, effectiveKeyCondition) ?? undefined` with `selectKvsQueryIndex(storeConfig, effectiveKeyCondition)?.partitionKey.key`. Nothing else changes: `ScanIndexForward` already honours `sortAscending`, and `LastEvaluatedKey` / `ExclusiveStartKey` are echoed back opaquely through `lastEvaluatedKeyToString` / `stringToLastEvaluatedKey`, so the composed index and primary key values round-trip untouched.

7. **`getKeyValueStoreUpdateActionProcessor.ts`**: pass `scoped.update(updates)` to `updateItem` instead of `updates`.

8. **`getKeyValueStoreScanAllScopesActionProcessor.ts`**: after decomposing the scope from the primary pk, strip the whole item with `stripScopedKvsItem(scope, item, [partitionKey, ...indexPartitionKeys])` (from `resolveScopeCarryingKvsAttributes(storeConfig, false)`) when `scope` is defined, rather than rewriting the pk alone. Otherwise migration reads would see composed index attribute values.

9. **`getEventGetRecordsActionProcessor.ts`** (stream records): `stripScope` only rewrites `GLOBAL_KVS_STREAM_PARTITION_KEY` on `newImage`/`oldImage`. Thread `qpqConfig` from `getProcessGetRecords` into `toInternalRecord`, resolve the store via `resolveKvsStoreConfigOrThrow(qpqConfig, GLOBAL_KVS_STREAM_STORE_NAME)`, and strip every scope-carrying attribute off both images with `stripScopedKvsItem`. The `keys` map only ever holds the primary pk/sk so its handling is unchanged.

### Dev server

10. **`quidproquo-dev-server/src/actionProcessor/core/keyValueStore/getKeyValueStoreQueryActionProcessor.ts`**: pass `selectKvsQueryIndex(storeConfig, keyCondition)?.partitionKey.key` as the `indexName` argument instead of `undefined`. The scoped validation call stays; it now accepts index-pk conditions because core does.

11. **`quidproquo-dev-server/src/actionProcessor/core/keyValueStore/getKeyValueStoreUpdateActionProcessor.ts`**: call the new `validateScopedKvsUpdateOrThrow` alongside the existing key validation, for parity with Dynamo.

12. **`quidproquo-dev-server/src/logic/keyValueStore/buildKvsKeyNarrowing.ts`**: generalise from fixed `pk`/`sk` columns to a pair of SQL key expressions. Add a `KvsKeyColumns = { pk: string; sk: Nullable<string>; pkAttribute: string; skAttribute: Nullable<string> }` type (own file under `logic/keyValueStore/`). For the primary table the expressions are `pk` / `sk` with the configured attribute names and the `'pk'`/`'sk'` aliases; for an index they are `json_extract(data, '$."<indexPk>"')` / `json_extract(data, '$."<indexSk>"')` with no aliases. Lift `toJsonPathLiteral` out of `ensureKvsTable.ts` into its own file so both use it. Behaviour for the primary path is unchanged.

13. **`quidproquo-dev-server/src/logic/keyValueStore/kvsPageCursor.ts`**: extend `KvsPageCursor` to `{ pk, sk, indexSk? }` and give `encodeKvsPageCursor` an optional `index: KvsIndex` argument that records the index sort value when paging an index. Primary-table cursors are byte-for-byte what they are today.

14. **`quidproquo-dev-server/src/logic/keyValueStore/SqliteKvsRepository.ts`**:
    - `query`: resolve `indexName` to `storeConfig.indexes.find((i) => i.partitionKey.key === indexName)` and pass it to `readPage`. An unknown name throws (misconfiguration, never silent).
    - `readPage` gains an optional `index`. When set: narrow with the index key expressions; add `<indexPkExpr> IS NOT NULL` (and `<indexSkExpr> IS NOT NULL` when the index has a sort key) so rows missing the indexed attributes are invisible, matching Dynamo's sparse GSIs; order by `<indexPkExpr> dir, <indexSkExpr> dir, pk dir, sk dir` so ties on the index sort value are stable; page with a row-value comparison `(<indexSkExpr>, pk, sk) > (?, ?, ?)` (or `<` descending; drop the `sk` leg for stores without a sort key). The JS re-evaluation via `evaluateKvsQueryOperation` still runs the full condition, so index selection only ever changes candidate order and paging, never membership.
    - `getAll` and `scan` keep ordering by the primary key.
    - Update the header comment on `readPage`, which currently states it always orders by `(pk, sk)`.

15. **`quidproquo-dev-server/src/logic/keyValueStore/kvsRepositoryContractTests.ts`**, in the existing `indexes` describe block, against the `people` store (`id` pk, GSI `email`/`age`) plus a store whose GSI has a string sort key:
    - a query on the index pk returns rows ordered by the index sort key ascending, and reversed when `sortAscending` is false, with items that share a primary pk order unaffected;
    - paginating an index query with `limit: 1` in both directions collects every row exactly once, including two rows with equal index sort values;
    - rows missing the index pk or sk are excluded from an index query;
    - the same index query under `tenant-a` and `tenant-b` returns only that scope's rows, and an unscoped query sees only unscoped rows;
    - a primary-key query on the same store is unaffected.
    Pass the index pk name as the `indexName` argument, as the processor now does.

### Migration

Rows already written to a scoped store that declares a GSI hold raw index attribute values, so after this change a scoped index query will not find them until they are rewritten. None of the affected stores (`TENANT_MEMBERSHIPS_STORE`, `QPQ_LOGS_STORAGE_DRIVE_NAME`, `QPQ_LOG_ACTIONS_KVS_NAME`, `QPQ_LOG_ENTITIES_KVS_NAME`, the event doc summary store) is currently written or queried under a scope, so no data breaks today; the tenant memberships GSI is also excluded from composition by the sort-key rule above. This plan ships the code change without a backfill and documents the rule in the `defineKeyValueStore` `indexes` doc comment: rows written to a scoped store before the index was scope-aware are not visible through a scoped index query. A backfill story (`askKeyValueStoreScanAllScopes` then re-upsert under each scope) can follow as its own issue if a scoped store with a GSI turns out to have live data.

## Open questions

- [ ] A GSI whose partition key is also a primary sort key (tenant memberships: `userId`/`tenantId` with GSI `tenantId`) stays unscoped under this plan, so a scoped query on that index keeps throwing. Is that acceptable, or should the sort key be composed everywhere too (which touches every keyed update and delete path)?
- [ ] The plan rejects scoping a store whose GSI partition key is number or binary typed, the same way a number-typed primary pk is rejected today. Should it instead allow the store and only reject scoped queries on that index?
