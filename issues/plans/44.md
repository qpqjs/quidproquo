# Issue #44: KVS: global secondary indexes are unusable on scoped (tenanted) stores; dev server ignores index ordering

**Verdict:** bug
**Status:** ready
**Branch:** `issue-44`

## Summary

On Dynamo the scope prefix is composed into the primary partition key value only, so a scoped query whose key condition names a GSI partition key throws (`queryMissingPartitionKey`), and even if it did not, the index partition would be shared by every tenant. On the dev server the sqlite engine ignores the index entirely: it narrows, orders and pages on the primary `pk`/`sk` columns, so a GSI query with `sortAscending: false` comes back in primary-key order.

The fix, per the reporter's amendment, keeps the user's index attribute untouched and gives every string-typed GSI partition key a framework-owned shadow attribute that holds the scope-composed value. The Dynamo GSI is defined on the shadow, reads strip shadows by name prefix so stored data never depends on the current index config, and a paged backfill action writes shadows onto rows that predate an index. The dev server gets index-aware narrowing, ordering and paging on the JSON row without any shadow storage.

## Affected packages

- `quidproquo-core`: `logic/scope/` composes, strips and validates the scope for exactly one attribute (`scopedKvsTranslator.ts`, `scopedKvsQueryOperation.ts`, `kvsScopeGate.ts`). The shadow attribute naming, the index-selection rule both backends need, and the backfill action all belong here.
- `quidproquo-actionprocessor-awslambda`: the query processor must target the shadow attribute, the update processor must keep shadows in lockstep with the user attribute, every read path (including scan-all-scopes and stream record images) must strip shadows, and the backfill action needs a processor. `getDynamoTableIndexByConfigAndQuery` moves to core.
- `quidproquo-deploy-awscdk`: `QpqCoreKeyValueStoreConstruct` defines each string-keyed GSI on the shadow attribute.
- `quidproquo-dev-server`: `SqliteKvsRepository.readPage`, `buildKvsKeyNarrowing`, `kvsPageCursor` and the query action processor never consider an index. The contract suite has no index-query cases. The backfill action needs a no-op processor.
- `quidproquo-features`: no code change, but its GSI-bearing stores (tenant memberships, websocket connections, log stores, event doc summary) are the migration surface.

## Approach

Terminology: a **shadowed index** is a GSI whose partition key is string-typed. Its **shadow attribute** is `__qpq_gsi_<partitionKey>` and always holds the value the index partitions on: `compose(scope, item[partitionKey])` for a scoped row, the raw `item[partitionKey]` for an unscoped row. One code path serves both. Index sort keys are never shadowed; they are isolated by living inside a scoped index partition. A GSI whose partition key is number or binary typed is not shadowed and keeps its index on the user attribute (see Open questions).

Because the user's attribute is never rewritten, the sort-key-doubling case (tenant memberships: pk `userId`, sk `tenantId`, GSI `tenantId`) needs no carve-out: keyed updates and deletes keep passing `tenantId` raw and the GSI partitions on `__qpq_gsi_tenantId`.

### Core

1. **`quidproquo-core/src/logic/keyValueStore/`** (new folder, `index.ts` barrel, exported from `logic/index.ts`), one export per file:
   - `KVS_GSI_SHADOW_ATTRIBUTE_PREFIX.ts`: the constant `'__qpq_gsi_'`.
   - `getKvsGsiShadowAttributeName.ts`: `(indexPartitionKey: string) => string`.
   - `isKvsGsiShadowAttributeName.ts`: prefix test, used by every strip.
   - `getShadowedKvsIndexes.ts`: `(storeConfig) => KvsIndex[]`, the string-keyed indexes.
   - `stripKvsGsiShadowAttributes.ts`: shallow-clone an item without any reserved-prefix attribute, by name only, never by config; returns the same object when nothing was removed.
   - `isKvsQueryCondition.ts`, `isKvsLogicalOperator.ts`, `flattenKvsQueryConditions.ts`, `selectKvsQueryIndex.ts`: moved from `quidproquo-actionprocessor-awslambda/src/logic/dynamo/qpqDynamoOrm/`. `selectKvsQueryIndex(storeConfig, keyCondition)` returns `Nullable<KvsIndex>` with today's rule unchanged (primary table wins if the primary pk is named, else the first GSI whose partition key is named; selection is on the user's attribute names). Move the tests with them, delete the originals, repoint the three ORM files that import the guards (`buildExpressionAttributeNames.ts`, `buildExpressionAttributeValues.ts`, `buildDynamoQueryExpression.ts`) to `quidproquo-core`. No re-export shim.

2. **`quidproquo-core/src/logic/scope/scopedKvsTranslator.ts`**: change `createScopedKvsTranslator(scope, pkAttributeName)` to `createScopedKvsTranslator(scope, storeConfig: KeyValueStoreQPQConfigSetting)`. The unscoped "non-string primary pk means no guards" rule moves inside. Methods:
   - `key`: unchanged.
   - `item`: drop any reserved-prefix attribute the caller passed in, compose the primary pk as today, then for each shadowed index whose partition key is present on the item (`!== undefined`) set the shadow to the composed value (scoped) or the raw value (unscoped, after `validateRawPkValueForScopeOrThrow`, since a raw value carrying the delimiter would forge a scoped index partition). A present non-string value on a string-typed index key throws via `composeScopedKvsValue`. Absent index attributes get no shadow, so sparse GSIs keep working.
   - `query: (keyCondition) => { keyCondition: KvsQueryOperation; indexName: Nullable<string> }` replaces `keyCondition`. It calls `selectKvsQueryIndex` on the caller's condition, then rewrites: primary pk legs are composed as today (a primary pk that is also an index sort key, as in tenant memberships, is stored composed, so its legs compose even inside an index query); when the selected index is shadowed, the leg(s) on that index's partition key are re-keyed to the shadow attribute with the composed (scoped) or raw (unscoped, delimiter-validated) value. The rewrite is index-aware on purpose: a primary-table query on tenant memberships (`userId = u AND tenantId = t`) must leave `tenantId` alone. Scoped rule: the condition must constrain the pk of whatever it targets, the primary pk for the primary table or the shadow for a shadowed index, else `queryMissingPartitionKey`. A scoped query whose target is a non-shadowed index throws the same error, as it does today.
   - `filter`, `scanFilter`: unchanged. The user's index attribute holds the raw value, so a filter leg on it needs no rewrite; only primary pk legs compose.
   - `strip`: strip the primary pk prefix as today, then `stripKvsGsiShadowAttributes`. The prefix strip applies in every translator, including the identity one, because unscoped rows carry shadows too.
   - `update: (updates: KvsUpdate) => KvsUpdate`: for each action whose `attributePath` is a top-level shadowed index partition key (a string, or a single-element array), append a companion action on the shadow: `Set` gets a `Set` with the composed or raw value, `SetIfNotExists` gets a `SetIfNotExists` likewise, `Remove` gets a `Remove`. `Add`, `Delete` and `Increment` on such an attribute are rejected (they cannot apply to a string key). An action that names a reserved-prefix path directly is rejected. Unscoped `Set`/`SetIfNotExists` values are delimiter-validated. Without this a scoped `askKeyValueStoreUpdate` that sets an index attribute would leave the row in the wrong index partition.
   - Rewrite the doc comment on `ScopedKvsTranslator` so it describes the pk plus shadow attributes.

3. **`quidproquo-core/src/logic/scope/scopedKvsQueryOperation.ts`**: add `rewriteKvsIndexPartitionKeyCondition(operation, indexPartitionKey, shadowAttributeName, scope)` that walks the tree, re-keys legs on the index partition key to the shadow and composes (or validates) their values, and returns the rewritten tree plus a count. `composeScopedKvsQueryOperation` and `stripScopedKvsItem` keep their signatures.

4. **`quidproquo-core/src/logic/scope/kvsScopeGate.ts`**:
   - `getScopedKvsTranslatorOrThrow`: pass the resolved `storeConfig` to the translator in both branches.
   - `validateScopedKvsKeyConditionOrThrow`: call `translator.query` and discard the result.
   - Add `validateScopedKvsUpdateOrThrow(qpqConfig, keyValueStoreName, scope, updates)` next to the other validation-only wrappers.
   - `resolveScopedPkAttributeOrThrow` is unchanged (scan and getAll on the dev server still only need the pk name).

5. **Backfill action, `quidproquo-core/src/actions/keyValueStore/askKeyValueStoreBackfillIndexAttributes.ts`**: `askKeyValueStoreBackfillIndexAttributesBase(keyValueStoreName, nextPageKey?) => { rewritten: number; nextPageKey?: string }` plus a draining story `askKeyValueStoreBackfillIndexAttributes(keyValueStoreName) => number`, in the same migration-only spirit as `askKeyValueStoreScanAllScopes`. It is a backend action rather than a story over scan-all-scopes for two reasons: reads strip shadows, so a story can never tell which rows differ; and rewriting only the shadow attributes with `UpdateItem` cannot clobber a concurrent write to the rest of the row, where a full re-upsert would. Paged so a Lambda never has to drain a whole table in one invocation. Add the error type, the `KeyValueStoreActionType` member, and register it in every processor index. Document on the requester: run it once after any deploy that adds a string-keyed GSI to a store, adds scope to a store that already has one, or lands this change.

### Lambda processor

6. **`getKeyValueStoreQueryActionProcessor.ts`**: `const { keyCondition: effectiveKeyCondition, indexName } = scoped.query(keyCondition)`, pass `indexName ?? undefined` to `query`. Drop the `getDynamoTableIndexByConfigAndQuery` import. `ScanIndexForward` already honours `sortAscending`; `LastEvaluatedKey` / `ExclusiveStartKey` round-trip opaquely through `lastEvaluatedKeyToString` / `stringToLastEvaluatedKey`, so shadow and composed values pass untouched.

7. **`getKeyValueStoreUpdateActionProcessor.ts`**: pass `scoped.update(updates)` to `updateItem`. The `ALL_NEW` return goes through `scoped.strip` already, which now removes shadows.

8. **`getKeyValueStoreScanAllScopesActionProcessor.ts`**: after decomposing the primary pk, run `stripKvsGsiShadowAttributes` on the item so migration reads never see shadows.

9. **`getEventGetRecordsActionProcessor.ts`** (stream records): `stripScope` also runs `stripKvsGsiShadowAttributes` on `newImage` and `oldImage`. No config needed, the strip is by name. `keys` only ever holds the table's pk/sk, so it is unchanged.

10. **`getKeyValueStoreBackfillIndexAttributesActionProcessor.ts`** (new): `Scan` the table one page at a time (no translator, raw rows), compute the expected shadow set for each row from `getShadowedKvsIndexes` and the scope decomposed from the primary pk, and for rows whose stored shadows differ (missing, stale, or orphaned from a removed index) issue one `UpdateItem` that `SET`s the expected shadows and `REMOVE`s the orphans. Return the count and the page key. Idempotent: a second run rewrites nothing. Note in the processor that a store with `onStream` will see one Modify record per rewritten row whose stripped images are identical.

### CDK

11. **`QpqCoreKeyValueStoreConstruct.ts`**: for each index, if `index.partitionKey.type === 'string'` define the GSI with `partitionKey: { name: getKvsGsiShadowAttributeName(key), type: STRING }`; otherwise keep the user attribute. Sort key stays the user attribute. Index name stays `index.partitionKey.key`. Note beside it that CloudFormation cannot change a GSI's key schema in place: the index is removed and re-created across stack updates, and DynamoDB limits GSI adds and removes per update. Existing stores with string GSIs will go through that replacement when this lands (see Migration).

### Dev server

12. **`quidproquo-dev-server/src/actionProcessor/core/keyValueStore/getKeyValueStoreQueryActionProcessor.ts`**: keep the scoped validation call, then pass `selectKvsQueryIndex(storeConfig, keyCondition)?.partitionKey.key` as `indexName` instead of `undefined`. The row-level scope column means no composing is needed locally; index selection only decides how sqlite narrows and orders.

13. **`quidproquo-dev-server/src/actionProcessor/core/keyValueStore/getKeyValueStoreUpdateActionProcessor.ts`**: call `validateScopedKvsUpdateOrThrow` alongside the existing key validation, so an update Dynamo rejects fails locally too. `applyUpdateToItem` is unchanged; there are no shadows to maintain.

14. **`quidproquo-dev-server/src/logic/keyValueStore/buildKvsKeyNarrowing.ts`**: generalise from fixed `pk`/`sk` columns to a pair of SQL key expressions. Add a `KvsKeyColumns = { pk: string; sk: Nullable<string>; pkAttribute: string; skAttribute: Nullable<string> }` type in its own file. For the primary table the expressions are `pk` / `sk` with the configured attribute names plus the `'pk'`/`'sk'` aliases; for an index they are `json_extract(data, '$."<indexPk>"')` / `json_extract(data, '$."<indexSk>"')` with no aliases. Lift `toJsonPathLiteral` out of `ensureKvsTable.ts` into its own file so both use it. Primary-path behaviour is unchanged.

15. **`quidproquo-dev-server/src/logic/keyValueStore/kvsPageCursor.ts`**: extend `KvsPageCursor` to `{ pk, sk, indexSk? }` and give `encodeKvsPageCursor` an optional `index: KvsIndex` argument that records the index sort value when paging an index. Primary-table cursors are byte-for-byte what they are today.

16. **`quidproquo-dev-server/src/logic/keyValueStore/SqliteKvsRepository.ts`**:
    - `query`: resolve `indexName` to `storeConfig.indexes.find((i) => i.partitionKey.key === indexName)` and pass it to `readPage`. An unknown name throws.
    - `readPage` gains an optional `index`. When set: narrow with the index key expressions; add `<indexPkExpr> IS NOT NULL` (and `<indexSkExpr> IS NOT NULL` when the index has a sort key) so rows missing the indexed attributes are invisible, matching Dynamo's sparse GSIs; order by `<indexPkExpr> dir, <indexSkExpr> dir, pk dir, sk dir` so ties on the index sort value are stable; page with a row-value comparison `(<indexSkExpr>, pk, sk) > (?, ?, ?)` (or `<` descending; drop the `sk` leg for stores without a sort key). The JS re-evaluation via `evaluateKvsQueryOperation` still runs the full condition, so index selection only ever changes candidate order and paging, never membership.
    - `getAll` and `scan` keep ordering by the primary key.
    - Update the header comment on `readPage`, which currently states it always orders by `(pk, sk)`.

17. **`quidproquo-dev-server/src/actionProcessor/core/keyValueStore/getKeyValueStoreBackfillIndexAttributesActionProcessor.ts`** (new): resolves the store (so an unknown store still fails), returns `{ rewritten: 0 }` with no page key. Nothing to backfill locally, and the contract must not differ in shape.

18. **`quidproquo-dev-server/src/logic/keyValueStore/kvsRepositoryContractTests.ts`**, in the existing `indexes` describe block, against the `people` store (`id` pk, GSI `email`/`age`) plus a store whose GSI has a string sort key:
    - a query on the index pk returns rows ordered by the index sort key ascending, and reversed when `sortAscending` is false, with items that share a primary pk order unaffected;
    - paginating an index query with `limit: 1` in both directions collects every row exactly once, including two rows with equal index sort values;
    - rows missing the index pk or sk are excluded from an index query;
    - the same index query under `tenant-a` and `tenant-b` returns only that scope's rows, and an unscoped query sees only unscoped rows;
    - a primary-key query on the same store is unaffected.
    Pass the index pk name as the `indexName` argument, as the processor now does.

### Migration

Every existing store with a string-keyed GSI has its index move from the user attribute to the shadow attribute when this lands: `TENANT_MEMBERSHIPS_STORE` (`tenantId`), the websocket connection store (`userId`), `QPQ_LOGS_STORAGE_DRIVE_NAME` (`runtimeType`, `fromCorrelation`), `QPQ_LOG_ACTIONS_KVS_NAME` (`actionType`, `linkKey`), `QPQ_LOG_ENTITIES_KVS_NAME` (`entityType`), and the event doc summary store (`type`, never selected because it is also the primary pk). Rows written before the deploy carry no shadow, so they are invisible to the moved index until `askKeyValueStoreBackfillIndexAttributes` runs against that store. This is real breakage for the unscoped queries in use today (tenant member lists, websocket lookups by user, log listings), not just for future scoped ones: the backfill has to run for each of these stores immediately after the deploy. The log stores expire through TTL, so a missed backfill there heals itself; tenant memberships and websocket connections do not.

The GSI key change is also a CloudFormation index replacement. Confirm the current limit on GSI adds and removes per stack update before scheduling the deploy, since the two log stores each carry two string GSIs and may need staged deploys.

The framework does not run the backfill automatically. A service wires it into a `defineDeployEvent` story, or runs it by hand; the requester doc says when.

## Open questions

- [ ] A GSI with a number or binary typed partition key gets no shadow under this plan, so its index stays on the user attribute and a scoped query on it keeps throwing. The alternative is to shadow it too, stringifying the value (a partition key is only ever compared for equality, so the string form loses nothing), which would make every index scope-capable at the cost of a string-typed shadow for a number key. Which do you want?
- [ ] Moving each GSI onto the shadow attribute is a CloudFormation index replacement under the same index name (remove in one update, add in the next). Keeping the name is the simplest for readers, but giving the new indexes a new name would let the add land before the remove. Keep the name and accept the staged deploys?
- [ ] Should the framework ship a built-in deploy event that runs the backfill for every store whose index config changed, or is wiring `askKeyValueStoreBackfillIndexAttributes` into a service's own deploy event enough for now?
