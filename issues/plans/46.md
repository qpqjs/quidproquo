# Issue #46: KVS query never selects a secondary index that shares the base table's partition key

**Verdict:** bug
**Status:** ready
**Branch:** `issue-46`

## Summary

A global secondary index whose partition key is also the store's primary partition key can never be selected: `getDynamoTableIndexByConfigAndQuery` returns the primary table as soon as the key condition names the primary partition key, so a `(pk, timeSk)` query goes to the base table and DynamoDB rejects it with `Query condition missed key schema element: sk`. The extra sort keys that become local secondary indexes are unreachable for the same reason. This is the index shape a scope-partitioned store needs, and the framework's own event doc summary store declares it (`(type, updatedAt)` on a store keyed `type` / `id`): `askEventDocListPage` says it lists newest first through that index, but the query actually runs on the base table ordered by `id`.

The fix, per the maintainer's direction, is named indexes: every index in the expanded form can carry a `name`, and `askKeyValueStoreQuery` gets an `indexName` option that targets one explicitly, bypassing inference. Inference itself is unchanged, so no existing query is re-routed.

## Affected packages

- `quidproquo-core`: `KvsIndex` and `defineKeyValueStore` (index names, uniqueness), `KeyValueStoreQueryOptions` (`indexName`, a new `IndexNotFound` error type), and a shared index-name resolver both backends call so an unknown name fails identically everywhere.
- `quidproquo-actionprocessor-awslambda`: the query processor honours the explicit index; `getDynamoTableIndexByConfigAndQuery` returns the index's name rather than its partition key attribute.
- `quidproquo-deploy-awscdk`: `QpqCoreKeyValueStoreConstruct` names each GSI from `index.name`.
- `quidproquo-dev-server`: the query processor resolves and forwards `indexName` instead of passing `undefined`; the sqlite index is named after the configured index.
- `quidproquo-features`: `defineEventDocSummary` names its `(type, updatedAt)` index and `askEventDocListPage` targets it.
- `quidproquojs.com`: `defineKeyValueStore` and `askKeyValueStoreQuery` docs.

## Approach

Index names are unique per store across GSIs and LSIs (DynamoDB requires it, since both share the table's index namespace). An LSI is named after its sort key attribute (`sortKeys[i].key` for `i >= 1`), as the CDK construct does today. A GSI defaults to its partition key attribute, which is what every deployed store is already named, so a store that does not opt into `name` sees no CloudFormation change.

### Core

1. **`quidproquo-core/src/config/settings/keyValueStore.ts`**: add `name: string` to `KvsIndex` and `name?: string` to `CompositeCompositeKvsIndex` (the bare-string form has no way to name and keeps the default). `convertCompositeKvsIndexToKvsIndex` resolves `name: compositeKvsIndex.name ?? partitionKey.key`. `defineKeyValueStore` throws when two entries resolve to the same name, or a GSI name collides with an LSI name (`sortKeys.slice(1)`), so the collision is a config-load failure and not a CDK synth failure. One-line JSDoc on `name`: it is the DynamoDB index name, defaults to the partition key attribute, and renaming a deployed index replaces it (CloudFormation removes and re-creates the GSI; DynamoDB backfills it from the table, but the index is unavailable in between).

2. **`quidproquo-core/src/logic/keyValueStore/`** (new folder with an `index.ts` barrel, exported from `logic/index.ts`; the same folder the #44 plan creates for `selectKvsQueryIndex`, so the two land side by side):
   - `listKvsIndexNames.ts`: `(storeConfig) => string[]`, every GSI `name` plus every LSI name. The one place the "extra sort keys are LSIs named after their attribute" rule lives; `defineKeyValueStore`'s uniqueness check uses it too.
   - `KvsIndexNotFoundError.ts`: shaped like `KvsStoreNotFoundError` (in `logic/scope/`), message names the store, the requested index and the valid names.
   - `resolveKvsQueryIndexNameOrThrow.ts`: `(storeConfig, indexName: string) => string`, returns the name when it is in `listKvsIndexNames`, else throws `KvsIndexNotFoundError`.

3. **`quidproquo-core/src/actions/keyValueStore/askKeyValueStoreQuery.ts`**: add `indexName?: string` to `KeyValueStoreQueryOptions` with a short comment (query this index instead of letting the processor infer one; a GSI or LSI name from the store's config; required when the wanted index shares the primary partition key, because inference always prefers the primary table then). Add `'IndexNotFound'` to `errorTypes`. `askKeyValueStoreQueryAll` picks the option up through its `Omit`. `askKeyValueStoreQuerySingle` takes positional options and stays as it is; a caller that needs an index on a single-row read uses `askKeyValueStoreQuery` with `limit: 1`.

4. **Scope**: no translator change. The scope is composed into the primary partition key attribute, so a scoped query on an index that shares that attribute already works once the index is selected. A scoped query on an index with a different partition key keeps throwing `queryMissingPartitionKey`; that is #44's problem, not this one. Note for #44: an index whose partition key is the primary partition key must not get a shadow attribute, because the primary attribute is already scope-composed and its shadow would either double-compose or duplicate it.

### Lambda processor

5. **`quidproquo-actionprocessor-awslambda/src/logic/dynamo/qpqDynamoOrm/getDynamoTableIndexByConfigAndQuery.ts`**: return `matchingIndex.name` instead of `matchingIndex.partitionKey.key`. Rewrite the doc comment: it currently states the partition key attribute is the index name, and it should say the primary table wins when the primary partition key is named, so an index sharing that key is only reachable through `indexName`. When #44 moves this function into core as `selectKvsQueryIndex`, the name lookup goes with it.

6. **`quidproquo-actionprocessor-awslambda/src/getActionProcessor/core/keyValueStore/getKeyValueStoreQueryActionProcessor.ts`**: pull the index choice out into a named `const` above the `query` call (per the code style rule on inline logic): `options?.indexName` set means `resolveKvsQueryIndexNameOrThrow(storeConfig, options.indexName)`, otherwise `getDynamoTableIndexByConfigAndQuery(storeConfig, effectiveKeyCondition) ?? undefined`. Map `KvsIndexNotFoundError` to `askKeyValueStoreQueryBase.errorType.IndexNotFound` in the `actionResultErrorFromCaughtError` table. `consistentRead` on a GSI is rejected by DynamoDB itself (`ValidationException`), which already surfaces as `ServiceUnavailable`; leave that alone.

### CDK

7. **`quidproquo-deploy-awscdk/src/constructs/feature/core/keyValueStore/QpqCoreKeyValueStoreConstruct.ts`**: `indexName: index.name` in the GSI loop. LSI naming is unchanged.

### Dev server

8. **`quidproquo-dev-server/src/actionProcessor/core/keyValueStore/getKeyValueStoreQueryActionProcessor.ts`**: resolve `options?.indexName` with `resolveKvsQueryIndexNameOrThrow` (store config via `resolveKvsStoreConfigOrThrow`) so an unknown name fails locally exactly as deployed, map `KvsIndexNotFoundError` to `IndexNotFound`, and pass the name to `repository.query` in place of the `undefined` placeholder. `SqliteKvsRepository.query` still ignores the argument (it narrows, orders and pages on the primary key), so locally an explicit index query returns the right rows in primary-key order. Index-aware ordering and paging on sqlite is #44 step 16; do not duplicate it here.

9. **`quidproquo-dev-server/src/logic/keyValueStore/ensureKvsTable.ts`**: name the sqlite expression index `${tableName}_gsi_${index.name}` instead of joining the attribute names, so it follows the configured name. `CREATE INDEX IF NOT EXISTS` means an existing dev database just gains the new index.

### Features

10. **`quidproquo-features/src/eventDoc/constants/eventDocSummaryUpdatedAtIndexName.ts`** (new, in the barrel): `EVENT_DOC_SUMMARY_UPDATED_AT_INDEX_NAME = 'updatedAt'`. **`defineEventDocSummary.ts`**: `indexes: [{ name: EVENT_DOC_SUMMARY_UPDATED_AT_INDEX_NAME, partitionKey: 'type', sortKey: 'updatedAt' }]`. **`askEventDocListPage.ts`**: pass `indexName: EVENT_DOC_SUMMARY_UPDATED_AT_INDEX_NAME`, which makes the story do what its doc comment already claims. This renames the deployed index from `type` to `updatedAt`, so every existing collection's summary GSI is replaced on the next deploy (see Open questions). `askEventDocList` drains the whole collection and does not care about order; leave it on the primary table.

### Docs

11. **`quidproquojs.com/docusaurus/docs/config/core/key-value-store.md`**: in "Indexes (GSIs)" document `name`, its default, the uniqueness rule with LSIs, the rename-is-replacement caveat, and the selection rule: a query is routed to the primary table when it names the primary partition key, otherwise to the first GSI whose partition key it names, and an index that shares the primary partition key (or any LSI) must be asked for with `indexName`. Fix the "On AWS" bullet, which says the GSI name is the partition-key attribute. **`ask-key-value-store-query.md`**: add the `indexName` row to the options table and the `IndexNotFound` row to the error table, with the `(pk, timeSk)` example from the issue.

## Open questions

- [ ] Naming the event doc summary index `updatedAt` replaces the deployed GSI (currently `type`) on every existing collection: CloudFormation removes it in one update and adds it in the next, and the index is empty until DynamoDB finishes backfilling. Keeping the default name (`type`) avoids that but leaves a misleading name on an index that sorts by `updatedAt`. Rename, or keep `type` and reference it through the constant?
- [ ] Inference is left as it is (primary table whenever the primary partition key is named), so the issue's `(pk, timeSk)` query still needs `indexName`. Should inference also learn this case (route to the first index that shares the primary partition key when the only sort condition is on that index's sort key), or is explicit-only the intended contract?
